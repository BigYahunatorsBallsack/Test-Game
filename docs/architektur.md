# Architektur: Dune Baron

Stand Paket 0.3. Grundlage: `docs/konzept.md`, `docs/umsetzungsplan.md`. Testfälle: `docs/testfaelle.md`.

## Ordner und Module

```
default.project.json     Rojo: Shared -> ReplicatedStorage, Server -> ServerScriptService, Client -> StarterPlayerScripts
src/shared/Data/         Datentabellen (Rarities, Tools, SandTypes, Zones, FindOdds, Finds, Crates, GemPacks, Products, Economy, UpgradeTree, World, Terrain, Tutorial)
src/shared/Logic/        Reine Logik ohne Roblox-API (DataCheck, Validate, RateLimiter, Profile, Migrations, BigNum, PlayerSession, Collecting, SandDig, PerfGuard, TreePurchase, Tutorial)
src/shared/Net/          RemoteSpec: Liste aller Remotes mit Schema und Rate-Limit
src/server/              init.server.luau (Bootstrap), Services/ (8 Services), Net/Net.luau
src/server/Data/         Datentabellen nur für den Server, nie zum Client repliziert (Codes, Paket 5.2)
src/client/              init.client.luau (Bootstrap), Controllers/ (State, Input, Hud, Dig, ToolVisual, ZoneMenu, Weather, SkillTree, UnlockPlayer, Tutorial; UnlockPlayer ist ein Hilfsmodul von SkillTree)
ServerPackages/          Wally-Pakete für den Server (ProfileStore), eingecheckt
wally.toml               Wally-Abhängigkeiten
tests/                   Lune-Tests (*.spec.luau), run.luau (Testläufer), lib/expect.luau
```

Regeln:

- Datengetrieben: Preise, Quoten, Raten, Zonen, Knoten stehen in `src/shared/Data`, nie im Logik-Code. Quoten sind ganze Zahlen in Hundertstel-Prozent (10000 = 100 %). Farben sind Hex-Text (`#RRGGBB`), Roblox-Typen kommen in `Data` und `Logic` nicht vor.
- Module in `src/shared` laden sich per relativem Pfad-String (`require("../Data/Tools")`), damit Lune und Roblox (Require-by-String) dieselben Dateien laden. Die Module bleiben flach, es gibt keine `init.luau`-Ordner in `src/shared`.
- Server und Client liegen in anderen Services als Shared. Dort laden Skripte Shared-Module per Instanz (`ReplicatedStorage.Shared...`), nicht per Pfad-String.
- Balance-Startwerte (Grundpreis, Tank, Fundchancen, Daily Reward) stammen aus `docs/balance/phase0_startwerte.md`. DataCheck prüft beim Serverstart, dass sie gesetzt und positiv sind.

`init.server.luau` startet so: Daten prüfen (`DataCheck.run`, bei Fehlern Abbruch mit allen Texten), Remotes anlegen, alle 8 Services laden, alle `Init()`, dann alle `Start()`, dann die optionalen `AfterStart()` (Abschlussprüfungen, bisher nur Shop: jedes Produkt mit ProductId hat einen Handler). Jeder Schritt wird im Output gedruckt.

### Controllers (Client)

`State` hält den vom Server gesendeten Zustand (`StateSync`) und die Meldungen (`Notify`). `Input` übersetzt Eingaben in Absichten (`SetCollecting`, `Sell`). `Hud` zeigt Münzen, Tank und Meldungen (schlichte Fassung bis zum UI-Paket). `Dig` verformt das Terrain beim Sammeln, nur auf diesem Client (Paket 1.4). `SkillTree` zeigt den Skilltree als Vollbild-Ebene (Paket 2.2, siehe unten), `Tutorial` zeigt Hinweistext, Strahl und Markierung der ersten 2 Minuten. `Sandstorm` zeigt Knopf, Vorschau-Fenster und die Sturm-Animation (Paket 2.7). `ZoneMenu` und `CollectionBook` sind die Fenster für Zonen und Sammlung (2.5, 2.6). `Screen` und `Graphics` sind Hilfsmodule ohne eigenen Controller-Eintrag (Paket 3.6, siehe unten).

## Datenfluss

Client -> Server: nur Absichten, nie Mengen oder Preise. Der Server berechnet alles aus Zeit, Stufen und Tabellen. Server -> Client: `StateSync` (Zustand zur Anzeige) und `Notify` (Meldungen).

Jede Client->Server-Remote durchläuft in `Net.on` vor dem Handler:

1. Profil geladen? (`PlayerData.isLoaded`, gesetzt in `PlayerData.Init`; vorher wird alles abgelehnt)
2. `Validate.check` gegen das Schema aus `RemoteSpec`: genaue Argumentzahl, Typ, NaN und Unendlich abgelehnt, Bereich, Länge, bekannte IDs.
3. `RateLimiter` (Token-Bucket pro Spieler und Remote).

`Net.init` verbindet jede Client->Server-Remote sofort mit dieser Prüfung (`OnServerEvent` bzw. `OnServerInvoke`), `Net.on` trägt nur den Handler ein (Fehler bei fehlendem Schema/Limit oder doppelter Registrierung). Besteht ein Aufruf die Prüfung, es gibt aber noch keinen Handler, wird er ohne Verstoß verworfen; RemoteFunctions antworten `{ ok = false, reason = "nicht verfügbar" }`. Verstöße werden verworfen und pro Spieler gezählt (`warn` mit Name und Grund), es gibt keinen Kick. Eine Remote ohne Schema oder Limit in `RemoteSpec` lässt sich nicht registrieren (`RemoteSpec.assertRegistrable` wirft einen Fehler).

## Profil und Migration

Das Profil ist ein versionierter Datensatz (`Profile.luau`, aktuelle Version in `Migrations.CURRENT_VERSION`). Felder: `version`, `coins {m,e}`, `tank {m,e}`, `gems`, `nodes`, `zones`, `currentZone`, `finds`, `windCrystals`, `prestiges`, `runEarned {m,e}`, `pity`, `inventory {skins, companions, toolVariants}`, `receipts`, `boosts {coinsUntil, luckUntil}` (`luckUntil` seit Paket 5.1, ohne neue Version), `passes {[passId] = true}` und `settings {autoDig}` (seit Version 6, Paket 4.4), `offers {[offerId] = {since, bought}}` (seit Version 7, Paket 4.5), `daily {streak, lastDay}`, `codes {[codeId] = true}` (eingelöste Codes, seit Paket 5.2, ohne neue Version), `lastSeen`, `createdAt`.

`Profile.migrate(data, migrations?)` gibt `(profile, status)` zurück:

- `"new"`: kein Profil vorhanden, es entsteht ein Standardprofil.
- `"ok"`: Profil ist aktuell oder wurde Schritt für Schritt migriert (`Migrations.steps[n]` hebt von Version n auf n + 1). Danach werden fehlende Felder tief mit Standardwerten gefüllt. Eine zweite Migration ändert nichts mehr.
- `"too_new"`: Das Profil hat eine höhere Version als der Server kennt. Es wird unverändert zurückgegeben und darf nicht gespeichert werden.

Weitere Regeln: Unbekannte Felder und unbekannte Knoten-IDs bleiben gespeichert und werden ignoriert (`Profile.ownedKnownNodes` filtert auf bekannte Knoten). Die Migration arbeitet auf einer Kopie. Fehlt ein Schritt, wirft sie einen Fehler, damit nichts Falsches gespeichert wird. Zu jedem Versionssprung gehört ein Schritt in `Migrations.steps` und ein Lune-Test.

## Laden und Speichern (Paket 1.1)

- Speicher: ProfileStore 1.0.3 (loleris) über Wally, DataStore `PlayerData_v1` (in Studio `PlayerData_Studio_v1`), Schlüssel `Player_<UserId>`. Laden gibt nach 120 s auf. ProfileStore übernimmt Sitzungssperre, Autosave und das Speichern beim Herunterfahren.
- Ablauf in `Logic/PlayerSession.luau` (rein, Lune-Tests mit Fake-Speicher in `tests/lib/fakestore.luau`): Sitzung öffnen, `Profile.migrate`, `Profile.sanitize`, dann gilt der Spieler als geladen.
- Profil zu neu, Öffnen fehlgeschlagen oder Migration mit Fehler: Spieler wird mit Meldung entfernt, die gespeicherten Daten bleiben unverändert.
- `Profile.sanitize` läuft beim Laden und vor jedem Speichern: Ein Feld mit falschem Typ oder einer Zahl NaN/unendlich wird einzeln auf den Standard gesetzt, Münzen/Tank ganz auf 0, ungültige Einträge in ID-Listen werden entfernt. Jede Reparatur erscheint als Warnung im Output.
- Schneller Rejoin auf denselben Server: Der neue Ladevorgang wartet, bis der alte abgebrochen ist (`isBusy`).
- Für Paket 4.1 (Käufe): Der Adapter braucht dann `Save` und `OnAfterSave`, damit `PurchaseGranted` erst nach dem Speichern kommt. Remote-Handler dürfen sich nicht auf Zustand verlassen, den `onLoaded`-Rückrufe erst nach einer Wartezeit setzen.
- Bekannte Grenze: Kommt ein Spieler zurück, während das letzte Speichern nach einem DataStore-Fehler noch wiederholt wird, können Änderungen seit dem letzten Autosave verloren gehen (selten, Prüfung in 6.1).
- Verlässt der Spieler das Spiel während des Ladens, wird die Sitzung sofort beendet. Übernimmt ein anderer Server die Sitzung, wird der Spieler hier entfernt.
- Vor jedem Speichern setzt der Server `lastSeen` (Grundlage für den Offline-Ertrag).
- Andere Services nutzen `PlayerData.get(player)`, `PlayerData.isLoaded(player)` und `PlayerData.onLoaded(fn)`.
- Ohne API-Zugriff in Studio nutzt ProfileStore einen Test-Speicher, der Server warnt dann im Output.
- Studio-Hilfe (nur in Studio): In der Befehlszeile (Ansicht Server) `game.Players.<Name>:SetAttribute("DebugCoins", 12345)` bzw. `"DebugGems"` setzt Münzen oder Gems im Profil.
- Wally-Pakete: `ServerPackages/` ist eingecheckt, damit `rojo serve` ohne Wally läuft. Nach einer Änderung an `wally.toml` einmal `wally install` ausführen.

## Sammeln, Tank, Verkaufen (Paket 1.2)

- Regeln in `Logic/Collecting.luau` (rein, Lune-Tests mit simulierter Uhr), der Service `Sand` schließt Remotes, Server-Uhr (`os.clock`), Händlerstand und `StateSync` an.
- Rate: Sand pro Sekunde des höchsten gekauften Werkzeugs (`Tools`, Knoten aus `UpgradeTree`; die Hand ist Start). Tank: `Economy.startTankCapacity` (Tank-Knoten in 2.1, Gamepass-Faktor in 4.4 über `capacityMultiplier`). Preis: `Economy.baseCoinsPerSand` mal Preisfaktor der Sandsorte der aktuellen Zone (unbekannte Zone: Dünenmeer). Boni folgen mit ihren Paketen.
- Der Client schickt `SetCollecting(true)` beim Drücken und danach alle `Economy.collecting.holdRefreshSeconds`, beim Loslassen `SetCollecting(false)`. Der Server rechnet nur Zeit bis `holdTimeoutSeconds` nach der letzten Auffrischung ab. Spam erzeugt keinen zusätzlichen Sand, weil nur Server-Zeit zählt.
- Der Tank enthält nur ganze Körner, Bruchteile bleiben im Speicher des Servers (`carry`). Ein voller Tank stoppt das Sammeln, `Notify { kind = "tankFull" }`.
- Laufendes Sammeln rechnet der Server alle 0,25 s ab und schickt bei Änderungen `StateSync { coins, tank, capacity, rate, toolId, collecting, zoneId, pricePerSand }`.
- Verkaufen: `Sell` geht nur im Abstand `World.sellStand.rangeStuds` zur Mitte eines Teils mit dem Tag `World.sellStand.tag`. Fehlt ein solcher Stand im Workspace, legt der Server einen Platzhalter mit Prompt "Verkaufen" an (bis Phase 3). Meldungen: `sold`, `tankEmpty`, `sellTooFar`.
- Eingabe: linke Maustaste, Gamepad R2 oder der eigene Knopf "Graben" (Handy, Paket 3.6). Die Taste E bleibt für Prompts frei.
- Sammeln nur mit lebendem Charakter und außerhalb der Reichweite eines Händlerstands (kein Sammeln direkt am Stand). Verkaufen verlangt, dass der Charakter auch bei der letzten Positionsprobe des Servers (alle 0,25 s) in Reichweite war, damit ein Teleport zum Stand für einen Aufruf nicht reicht.
- Noch offen: ob der Spieler beim Sammeln auf Sand der Zone steht (mit der Welt, Phase 3). In Paket 2.5 (Reisen) muss der Preis an die Zone gebunden werden, in der der Sand gesammelt wurde (oder an die Zone des Stands), sonst lässt sich billiger Sand in teuren Zonen verkaufen. Beim Verlassen können bis zu `holdTimeoutSeconds` Sand fehlen.

## Terrain-Verformung (Paket 1.4)

- Nur auf dem Client: Der Controller `Dig` gräbt, solange der Spieler hält und der Server das Sammeln bestätigt (`StateSync.collecting`, Tank nicht voll). Terrain-Änderungen eines Clients erreichen weder Server noch andere Spieler. Der Server zählt den Sand unabhängig davon wie in 1.2.
- Zahlen in `Data/Terrain.luau`, Regeln in `Logic/SandDig.luau` (Lune-Tests mit Fake-Welt), Bildraten-Wächter in `Logic/PerfGuard.luau`. Der Controller liest und schreibt nur Voxel (`ReadVoxels`/`WriteVoxels`), zeigt Partikel und die Rückfallvariante.
- Loch: Strahl nach unten `dig.forwardStuds` vor dem Charakter. Nur Terrain aus `diggableMaterials` (Sand). Alle `dig.intervalSeconds` schneidet eine Kugel (`holeByTool[toolId].radius`) die Oberfläche `depth` tief an. Das Terrain wird als Höhenfeld behandelt, weil Voxel 4 Studs groß sind. Fels und Wasser bleiben. Tiefengrenze: `dig.maxDepthStuds` unter der Oberfläche, die beim ersten Graben an der Stelle gemessen wurde.
- Blöcke: Terrain wird in Würfeln von `chunkSize` (16) Studs verwaltet. Vor dem ersten Graben merkt sich der Client den Originalzustand des Blocks. Nach `regrow.delaySeconds` ohne neues Graben blendet er den Block in `regrow.steps` Schritten über `regrow.seconds` zurück und vergisst ihn. Höchstens `regrow.maxWritesPerUpdate` Blöcke pro Bild, höchstens `regrow.maxDirtyChunks` offene Blöcke (darüber wird der älteste sofort zurückgesetzt). Ein Block näher als `regrow.blockRadiusStuds` am Charakter wartet, damit niemand im Sand stecken bleibt.
- Rückfallvariante: Liegt die Bildrate `perf.downAfterSeconds` lang unter `perf.lowFps`, schreibt der Client kein Terrain mehr, sondern zeigt eine sinkende Sandscheibe und Partikel. Zurück bei über `perf.highFps` für `perf.upAfterSeconds`, höchstens `perf.maxSwitches` Wechsel. Zum Testen: `game.Players.LocalPlayer:SetAttribute("DigMode", "fallback")` (oder `"full"`, `nil` = automatisch) in der Client-Befehlszeile.
- Anzeige für den Handy-Test (`debug.showOverlay`): Modus, FPS und offene Blöcke oben links unter dem HUD. Vor dem Launch abschalten.
- Platzhalter-Sandfeld: Liegt am Feld `placeholderField` noch kein Terrain, legt der Server beim Start ein Sandfeld an (Warnung im Output) und färbt das Material nach der Sandsorte. Mit der echten Zone (Paket 1.5) `enabled = false` setzen.
- Bekannte Grenzen: Mit StreamingEnabled kann ein Block, der aus- und wieder eingeblendet wird, vor dem Nachwachsen schon im Originalzustand sein (harmlos). Ändert der Server später Terrain in einem offenen Block, überschreibt das Nachwachsen diese Änderung bei diesem Spieler bis zum nächsten Laden. Das Koloss-Event (5.6) braucht deshalb eine eigene Lösung. Die Sandfarbe ist global pro Material (`SetMaterialColor`), Zonen mit anderen Sandsorten brauchen in 2.5 eigene Materialien oder Material-Varianten.

## Mini-Kauf und Tutorial (Paket 1.6)

- Neue Knoten in `UpgradeTree` (Werte aus `docs/balance/phase0_startwerte.md`): `collect_rate_1` (15 Münzen, +50 % Sammelrate), `tank_1` (20, Tank 30), `tank_2` (60, Tank 60), `tank_3` (250, Tank 150), `collect_rate_2` (120, +25 %, nach der Schaufel). Jeder Knoten hat jetzt `name` und `description`. Wirkungen: `rateBonus` (bp, Boni addieren sich auf die Grundrate des Werkzeugs), `setTank` (Gesamtgröße, der höchste gekaufte Wert zählt, der Gamepass-Faktor kommt danach).
- Kauf in `Logic/TreePurchase.luau` (rein): `check` und `buy` prüfen bekannt, nicht vergeben, nicht gekauft, Voraussetzungen, Münzen (in dieser Reihenfolge) und liefern den Grund (`unknown`, `granted`, `owned`, `requires`, `coins`). Der Kauf läuft ohne Warten im selben Aufruf, ein Doppelklick trifft deshalb auf `owned`. `Upgrades` hängt `PurchaseNode` daran, nach Erfolg ruft es `Sand.refresh(player)` (Tutorial neu bewerten, Zustand senden). 2.1 baut den ganzen Baum auf diesem Kauf auf.
- `StateSync` hat zwei neue Felder: `nodes` (gekaufte, bekannte Knoten) und `tutorialStep`.
- Tutorial: Schritte und Texte in `Data/Tutorial.luau`, Fortschritt in `Logic/Tutorial.luau` (rein), gespeichert als `profile.tutorial.step` (1 bis 4 = Schritt, 5 = fertig, nie zurück). Bedingungen: `tankAtLeast` (15 Sand), `sold` (Ereignis vom Server), `node` (zählt auch beim Laden, erledigte Schritte entfallen). Das Feld wird bei alten Spielständen von `Profile.migrate` mit Schritt 1 gefüllt, die Profilversion bleibt 1.
- Anzeige: `Tutorial` (Client) zeigt Text oben und einen Strahl zum Ziel (Teile mit dem Tag `World.sandField.tag` bzw. `World.sellStand.tag`, sonst das Platzhalter-Sandfeld aus `Data/Terrain`). Der Knopf "Baum" (`SkillTree`) erscheint ab `Tutorial.showUpgradesFromStep`, pulsiert, solange der Schritt auf einen Baumknoten zeigt, und im Baum leuchtet der Knoten des aktuellen Schritts (`highlightNodeId`). Das Tutorial-Ziel `tree` zeigt keinen Strahl.
- Zielzeiten: Eine Lune-Simulation mit den echten Regeln (5 s Weg je Richtung, billigsten sichtbaren Knoten kaufen) ergibt das erste Upgrade nach 20 s und die Schaufel nach 120 s, wie `Economy.targetSeconds`.
- Das Tutorial schickt schon bei 15 Sand zum Verkauf, auch bei größerem Tank (zum Beispiel mit dem Gamepass "Großer Tank", 4.4). Verkaufen geht mit jedem nicht leeren Tank, der Server prüft die Reichweite zum Händlerstand wie in 1.2.

- Security-Review 1.6: kein kritischer Befund (kein Kauf ohne Voraussetzung, Münzen oder doppelt). Eingearbeitet: Sandsturm-Knoten sind nie kaufbar, DataCheck verlangt Preis über 0 für kaufbare Knoten, Fehler in der Anzeige nach dem Kauf melden keinen Fehlschlag mehr. Bekannt und offen: (a) Münzen über etwa 1e15 runden kleine Preise auf 0 (Eigenschaft des Zahlentyps, kein Gewinn, in 2.1 beachten). (b) Eine Raten-Änderung gilt rückwirkend für das offene Abrechnungsfenster (höchstens 0,25 s, etwa 1 Sand). (c) Verkaufen per Teleport zum Stand: Die Position bestimmt der Client, ein Teleport hin und zurück spart den Weg und verkürzt die frühen Zeiten. Mit Käufen für Münzen lohnt sich das, die Prüfung (mehrere Proben in Reichweite oder Geschwindigkeitsgrenze) gehört in Paket 6.1.

## Skilltree (Paket 2.1)

- `Data/UpgradeTree.luau` enthält den ganzen Baum des ersten Laufs (Hand bis Großmaschine) mit den Ästen `collect` (Rate und Werkzeuge), `tank`, `sell` und `luck`, dazu `sandstorm_1`. Zahlen und Simulation: `docs/balance/skilltree_2_1.md` und `.py`. Verkauf und Glück beginnen nach der Schaufel, damit die ersten 2 Minuten aus 1.6 gleich bleiben. Werkzeuge verlangen nur das vorige Werkzeug (Entscheidung 18.11.2026: keine Raten-Sperren). Saugroboter und Großmaschine kommen darum bald nach dem Mini-Bagger, bis Paket 6.4 die Werkzeugpreise anhebt.
- Wirkungen: `setTool`, `rateBonus`, `setTank`, neu `sellBonus` (bp auf den Münzpreis pro Sand) und `luckBonus` (bp auf die Fundchance, wirkt ab 2.6). Boni eines Typs addieren sich. `DataCheck` verlangt, dass jede Wirkung in ihrem Ast steht.
- `Logic/TreeEffects.luau` (rein) berechnet alle Wirkungen bei jedem Aufruf aus den gekauften IDs und der aktuellen Tabelle: Werkzeug, `rateBonusBp`, `tankCapacity`, `sellBonusBp`, `luckBonusBp`, dazu `sellMultiplier` und `luckMultiplier`. `Collecting` liest Rate, Tank und Preis daraus. Beim Verkauf zählen nur ganze Münzen.
- Gespeichert werden nur die gekauften IDs (`profile.nodes`), nie Werte. Baum-Updates brauchen darum keine Migration: Entfernte IDs bleiben gespeichert und wirken nicht (keine Erstattung), neue Knoten werden kaufbar, sobald ihre Voraussetzungen erfüllt sind, ein gekaufter Knoten wirkt auch, wenn ein Update ihm eine neue Voraussetzung gibt, und geänderte Werte gelten sofort. Nur das Umbenennen einer ID braucht einen Schritt in `Migrations`.
- `TreePurchase.nodeState` und `treeState` liefern für den Baum in 2.2 den Zustand jedes Knotens: `owned`, `available` (Voraussetzungen erfüllt, Geld egal) oder `fog`. Vergebene Knoten sind nie `available`.
- `StateSync` hat zwei neue Felder: `sellBonusBp` und `luckBonusBp`. `pricePerSand` enthält den Verkauf-Ast schon.
- Vor jedem Kauf rechnet `Upgrades` über `Sand.settle(player)` das offene Sammelfenster mit der alten Rate ab, damit eine neue Rate nicht rückwirkend gilt (offener Punkt b aus 1.6 damit erledigt).
- Security-Review 2.1: kein kritischer oder hoher Befund. Eingearbeitet: `BigNum.floor` lässt ganze Zahlen ganz (vorher kostete das Abrunden beim Verkauf bei 115 Sand eine Münze), `TreePurchase` bucht bei kaputtem `nodes`-Feld nichts ab, `Profile.ownedKnownNodes` zählt nur `true`, `DataCheck` verlangt ganze Preise, entfernte Knoten-IDs werden nie wiederverwendet. Bekannt: Profile, die unter dem Baum aus 1.6 schon Mini-Bagger oder später gekauft haben (nur Studio-Tests), behalten sie und umgehen die neuen Raten-Sperren. Offen bleiben (a) Rundung kleiner Preise ab etwa 1,5e16 Münzen (harmlos) und (c) Verkaufen per Teleport (Paket 6.1).

## Skilltree-Ansicht (Paket 2.2)

Der Baum entsteht aus den Daten. Keine neue Remote, kein neues Profilfeld: Der Client schickt weiter nur `PurchaseNode(id)`, alle Werte kommen aus `StateSync`.

- `Data/TreeLayout.luau`: Spalte je Wirkung (Glück, Tank, Werkzeuge in der Mitte, Rate, Verkauf, Sandsturm), Abstände, Knotengröße, Zoomgrenzen, Tipp-Schwelle und die Platzhalter-Zeichen und -Farben (bis Stil-Guide 0.4 und Icons 3.1). Ein neuer Ast braucht hier eine Spalte, ein neuer Knoten nichts. `UpgradeTree`-Knoten dürfen ein optionales `pos = { column, row }` tragen, das den Platz festnagelt.
- `Logic/TreeLayout.luau` (rein): rechnet aus `UpgradeTree` den Platz jedes Knotens. Spalte aus der Wirkung, Band aus dem höchsten verlangten Werkzeug (jedes Werkzeug öffnet ein Band), Reihe über den Voraussetzungen derselben Spalte. Die Bänder stapeln sich von unten nach oben, darum verschiebt ein neuer Knoten oben nie die Knoten darunter. Koordinaten: x nach rechts, y nach unten, der Start liegt bei (0, 0).
- `Logic/TreeView.luau` (rein): Zustand je Knoten aus `TreePurchase.nodeState` und den Münzen: `owned`, `affordable`, `expensive`, `silhouette` (im Nebel, aber alle Voraussetzungen gekauft oder kaufbar, ohne Name und Preis) oder `hidden` (dazu vergebene Knoten wie `sandstorm_1`). Dazu die Linien (nur gerade, senkrecht, innerhalb einer Spalte: `lit`, `dim`, `dashed`), die Bandlinien, "Braucht" je Knoten, der Zähler bezahlbarer Knoten und der Fokus-Knoten beim Öffnen (Tutorial-Knoten, sonst billigster bezahlbarer, sonst billigster kaufbarer, sonst Start).
- `Logic/TreeCamera.luau` (rein): Zoom um einen Punkt, Pinch, Verschieben mit Randbegrenzung (kleiner Baum steht mittig), Tippen (unter `tapMaxMovePixels`) oder Ziehen, Treffertest, Zentrieren.
- `Controllers/SkillTree.luau` zeichnet nur: Vollbild-Ebene, Baumfläche mit `UIScale`, Knoten als Frames (Treffer per eigenem Test, nicht per Knopf), gerade Linien, Nebel als Verlauf über dem obersten sichtbaren Knoten, Karte mit Kaufen-Knopf (unten am Handy, rechts am PC), Plus/Minus, Mausrad und Zwei-Finger-Geste. Gekauft wird nur über den Kaufen-Knopf. Solange der Baum offen ist, pausiert `Input.setSuspended` das Sammeln. Die Freischalt-Sequenz steht im Abschnitt zu Paket 2.3.
- `DataCheck` prüft die Layout-Zahlen (eindeutige Spalten, Zoomgrenzen, Mindest-Tippgröße) und `pos` (Spalte, Reihe, Kollision).

## Freischalt-Sequenz (Paket 2.3)

Keine neue Remote, kein neues Profilfeld. Ausgelöst wird die Sequenz nicht durch den Klick, sondern durch den Vergleich zweier `StateSync`-Zustände: Ein Knoten, der neu in `nodes` steht, wurde gekauft. Der erste Zustand nach dem Beitreten hat keinen Vorgänger und zählt nie. Sie läuft nur bei offenem Baum.

- `Data/UnlockAnimation.luau`: Schritte (`press`, `ring`, `pulse`, `reveal`, `camera`, `flash`) mit `start` und `duration` je Variante, dazu `shortAfterPurchases` (10), `pressScale`, `revealStartScale`. Varianten: `normal` (1,2 s), `milestone` (1,6 s, Knoten mit `milestone`, dazu größerer Ring und Aufhell-Puls, gilt immer) und `short` (0,5 s, ab dem elften Kauf einer Sitzung, ohne Lichtimpuls).
- `Data/TreeSounds.luau`: vier Cues (`press`, `ring`, `reveal`, `milestone`) mit `soundId`, `volume`, `pitch`. Die IDs sind leer, bis Paket 3.5 echte Sounds liefert. Eine leere ID spielt nichts und ist kein Fehler.
- `Logic/UnlockSequence.luau` (rein): `diff` (neu gekaufte Knoten), `variantFor`, `plan` (Variante, Zeitleiste, neu sichtbare Knoten aus dem Vergleich zweier `TreeView`-Zustände, Impulskanten nur in derselben Spalte, Glanzziele für Folgeknoten ohne Linie, Kamerapunkte, Töne mit Zeitpunkt).
- `Controllers/UnlockPlayer.luau` (Hilfsmodul von `SkillTree`) spielt den Plan mit Tweens ab: Eindrücken, Ring, Lichtpunkte über die Linien, Schleier und Nebel weichen, Aufhell-Puls, Kamerafahrt per `Heartbeat`. `stop()` springt ans Ende und räumt alle kurzlebigen Instanzen ab. Ein neuer Kauf, das Schließen des Baums und das Ziehen oder Zoomen des Spielers (nur die Kamerafahrt) beenden die laufende Sequenz.
- `DataCheck` prüft Reihenfolge der Starts, Gesamtdauer (höchstens `maxTotalSeconds`), kurze Variante kürzer und Meilenstein länger als normal, Tonzuordnung und Sound-IDs (leer oder `rbxassetid://` plus Ziffern).

## Zahlentyp

`BigNum = { m: number, e: number }` (Wert = m * 10^e, Mantisse in [1, 10)). Paket 0.3 lieferte `new`, `zero`, `serialize` und `deserialize`, Paket 1.2 `add`, `sub`, `mul`, `mulNumber`, `div`, `compare`, `lt`, `eq`, `max`, `min`, `floor` und `toNumber`. Die Mantisse wird auf 14 Nachkommastellen gerundet, damit ganze Zahlen ganz bleiben; `toNumber` gibt ganze Zahlen unter 10^15 exakt zurück. Paket 1.3 lieferte `format(zahl, stellen?)` und die Tests in `tests/bignum.spec.luau`. Anzeige: deutsches Komma, Suffixe K, M, B, T, Qa, Qi, Sx, Sp, Oc, No, Dc (Konstante `BigNum.SUFFIXES`), ab 10^36 wissenschaftlich (`1,23e36`). Standard ist eine Nachkommastelle (`BigNum.DEFAULT_DECIMALS`, wählbar 0 bis 4), Endnullen entfallen (`1K`, `1,5K`), Hälften runden auf, und an den Stufengrenzen springt die Anzeige weiter (999,96K wird `1M`, nie `1000K`). Das HUD zeigt alle Münz- und Sandwerte über `BigNum.format`.

## Zonen 2 bis 5 (Paket 2.5)

- **Welt:** `Data/World.zones` legt die fünf Zonen nebeneinander entlang der x-Achse (je 192 Studs breit, aus `ZONE_ORDER` erzeugt): Bereich (`bounds`), Spawn, Platzhalter-Stand, Platzhalter-Sandfeld und Tor zur Zone davor. `World.zonesById` ist die Suchtabelle. `DataCheck` prüft, dass jede Zone einen Bereich hat, Spawn und Stand darin liegen und nichts überlappt.
- **Freischaltung:** Eine Zone ist frei, wenn ihr `requires`-Knoten gekauft ist oder sie schon in `profile.zones` steht (`Logic/Zones.isUnlocked`). `unlockNew` schreibt neu erfüllte Zonen ins Profil und meldet jede nur einmal. Beim Laden läuft es still, nach einem Kauf meldet der Server `zoneUnlocked`. Gespeicherte Zonen bleiben frei, auch wenn ein Baum-Update den Knoten verschiebt.
- **Position gehört dem Client, die Entscheidung dem Server:** `ZoneService` prüft alle 0,25 s mit `Zones.resolve`, in welcher Zone jeder Spieler steht. Eine freie Zone wird zur aktuellen Zone (`Sand.setZone`: erst mit der alten Sandsorte abrechnen), eine gesperrte nie: Der Spieler wird an den Rand der aktuellen Zone zurückgesetzt (Abweichung vom Plan: nicht zum Spawn, damit Zufallsberührungen am Tor nicht bestrafen), Meldung `zoneLocked` höchstens alle 2 s. Ist die aktuelle Zone selbst gesperrt oder unbekannt (zum Beispiel nach einem Sandsturm, Paket 2.7), liefert `Zones.resolve` die Art `reset` und der Spieler geht zum Dünenmeer-Spawn; dasselbe passiert beim Laden. Nach jedem Teleport gilt 0,5 s Schonfrist, damit der Spieler nicht doppelt zurückgesetzt wird (`character:PivotTo`). Die Tor-Anzeigen (`ZoneGate`-Tag) sind nur Optik, die Sperre ist die Prüfung des Servers.
- **Reisen:** Die vorhandene Remote `TravelZone(zoneId)` (Schema und Rate-Limit schon aus 0.3) antwortet `{ ok, reason }`. Der Server prüft `Zones.canTravel` (unbekannt, gleiche Zone, gesperrt, Abklingzeit `World.travelCooldownSeconds`), setzt die Zone und teleportiert zum Spawn.
- **Gemischter Tank:** `profile.tank` bleibt die Gesamtmenge, `profile.tankMix` (neu, Version 2) merkt sich den Sand je Sandsorte. `Collecting.update` schreibt gesammelten Sand in die Sorte der aktuellen Zone, `Collecting.sell` zahlt jede Sorte mit ihrem eigenen Faktor an jedem Stand. Was im Tank, aber nicht im Mix steht (Debug-Werte, kaputte Einträge), zahlt die billigste Sorte (nie mehr als der Tank, `BigNum.min`), damit sich über einen kaputten Mix kein Gewinn holen lässt. `Collecting.addSand` und `Collecting.clearTank` halten Tank und Mix zusammen; `Profile.sanitize` leert einen Mix bei leerem Tank und entfernt kaputte oder negative Einträge. Migration `Migrations.steps[1]`: der alte Tank wird zu Sand der Zone, in der der Spieler stand (Zuordnung fest eingetragen, damit Tabellen-Updates sie nicht ändern).
- **Sandsorten:** `SandTypes.terrainMaterial` gibt jeder Sorte ein eigenes Roblox-Terrain-Material (Sand, Sandstone, Salt, Glacier, Basalt), weil Roblox nur eine Farbe je Material kennt. Der Server füllt die Platzhalter-Felder und setzt die Farben (`SetMaterialColor` aus `colorHex`). `Dig` grabt in allen diesen Materialien. `Terrain.dig.maxDepthByZone` gibt dem Canyon eine größere Tiefengrenze (`SandDig.tryDig(..., zoneId)`).
- **Wetter:** `Data/Weather` (Zeitplan und Aussehen je Zone) und das reine Modul `Logic/Weather.stateAt(zoneId, serverZeit)`: ein fester Zyklus aus der Serverzeit, alle Clients sehen dasselbe ohne Remote. `Controllers/Weather` zeigt Regen und Staubwind als Partikel um die Kamera und Nebel/Dunst über Atmosphäre und Farbkorrektur, mit weichen Übergängen. In 2.5 ist das Wetter nur Optik, `findChanceBonusBp` liest Paket 2.6.
- **Client:** `Controllers/ZoneMenu` (Knopf "Zonen", Liste mit Sandsorte, Status und Reisen-Knopf, Tor-Anzeigen mit Schild). `Hud` zeigt Zone, Werkzeug und Rate und die Meldungen `zoneUnlocked`, `zoneEntered` und `zoneLocked`.
- **Entschieden in 2.7 (18.11.2026):** Der Sandsturm sperrt Oase, Canyon und Salzsee wieder und die Ruinenstadt braucht in jedem Lauf den Knoten `sandstorm_ruins`.

## Fundstücke, Reveal und Sammlung (Paket 2.6)

- **Funde entstehen nur aus echter Sammelzeit.** `Collecting.update` zählt in `state.findSeconds` (je Zone), wie lange Sand wirklich in den Tank floss. Läuft der Tank in einem Fenster voll, zählt nur die Zeit bis "voll". Alle Aufrufe (Halten, Verkaufen, Kaufen, Zonenwechsel) landen im selben Zähler, `Collecting.takeFindSeconds` holt ihn ab. Es gibt keine neue Remote vom Client zum Server.
- **Würfeln (`Logic/FindRoll`, rein, Zufall als Funktion):** Chance pro Sekunde = `findChancePerSecond` × `zoneFindChanceFactor` × Glück-Ast × (1 + Regen-Bonus mal Stärke). Im Fenster 1 − (1 − p)^t. Die Seltenheit kommt aus `FindOdds.zoneOddsTable` (heute alle `base`), danach ein gleichverteilter Fund der Zone mit dieser Seltenheit (fehlt sie, die nächst tiefere). Glück ändert nur die Chance. Wert = `findBaseValue` × Sandfaktor × Grundrate des Werkzeugs × Wertfaktor, beim Fund festgeschrieben (kein Knoten-Bonus, kein Sammlungsbonus).
- **Erster Fund sicher:** Ohne bekannten Fund und nach `firstFindGuaranteeSeconds` (60) Sitzungs-Sammelzeit kommt ein Gewöhnlicher Fund.
- **Sammlung (`Logic/Collection`, `Data/Collection`):** Gespeichert wird nur `profile.finds` (ID → Anzahl, keine Migration). Slots, Sets, Bonus und Zonenbücher werden daraus berechnet. Der Bonus (`setBonusBp` je Set-Nummer) ist ein eigener Faktor auf die Münzen pro Sand (`Collecting.pricePerSand` und `priceOf`), wirkt in allen Zonen und nicht auf Fundwerte. Ein Zonenbuch (6 von 6 Sets) nennt Titel und Werkzeug-Skin, beides ist in 2.6 nur Anzeige.
- **Doppelte Funde** werden sofort für ihren festen Wert verkauft (Entscheidung 18.11.2026): `Collection.record` zählt hoch und bucht die Münzen als BigNum.
- **Fundliste:** 150 Platzhalter mit festen IDs `<zone>_s<set>_<slot>`. Paket 3.3 ändert nur Namen und Beschreibungen. `DataCheck.checkCollection` prüft: 5 Funde je Set, ID-Muster, jede Seltenheit in jeder Zone, Set-Boni, Zonenbücher, `zoneOddsTable`.
- **Server (`Services/Finds`):** Alle 0,25 s `Sand.takeFindSeconds` abholen, würfeln, `Collection.record`, dann `Notify { kind = "find", ... }` (Fund, Seltenheit, neu oder doppelt, Münzen, Set-Stand, `setCompleted`, `zoneBookCompleted`, Bonus), `CollectionSync` (Zähler, Bonus, Bücher) und `Sand.refresh`. Studio-Hilfe: Attribute `DebugFindSet` und `DebugFindZone` am Spieler füllen ein Set oder eine Zone (nur in Studio).
- **Client:** `Controllers/Reveal` (Warteschlange, Objekt im Sand, kleine Karte bis Ungewöhnlich, große Karte mit Aufladen und Lichtstoß ab Selten, Blitz bei Mythisch, Banner für Set und Zonenbuch, Tipp überspringt, ohne Effekte im Rückfallmodus) und `Controllers/CollectionBook` (Knopf "Sammlung", Reiter je Zone, 6 Sets mit 5 Slots, Bonus). `State` hält die Sammlung (`getCollection`, `onCollectionChanged`). Sounds sind leere IDs bis Paket 3.5.
- **Client-Start:** `init.client` startet jeden Controller in `pcall`, damit ein Fehler (zum Beispiel ein in Studio fehlender Enum-Wert) die folgenden Controller nicht verhindert.
- **Offen:** Fundstellen im Nebel des Salzsees, Offline-Funde (5.3), Titel über dem Kopf und Werkzeug-Skin als Optik. Der Starterpaket-Auslöser kam mit 4.5 (`Finds.addFindListener`, siehe "Shop und Angebote").

## Sandsturm (Paket 2.7)

- **Ablauf:** Der Knopf "Sandsturm" erscheint, sobald `Economy.sandstorm.requiresNode` (`collect_tool_4`, Canyon frei) gekauft ist. Das Fenster zeigt die Vorschau des Servers (Kristalle jetzt, Bonus davor und danach, Einnahmen des Laufs) und die Liste "wird zurückgesetzt" und "bleibt". "Sturm auslösen" fragt mit einem zweiten Tipp nach, dann ruft der Client `Prestige` ohne Werte auf. Danach zieht eine Sandwand über den Bildschirm, ein Banner nennt die neuen Kristalle und den Bonus.
- **Kristalle (`Logic/Sandstorm`, rein):** `floor(crystalScale × (Einnahmen / crystalUnit) ^ crystalExponent)` aus `Economy.sandstorm`, gerechnet über den Logarithmus (kein Überlauf), höchstens `maxCrystals` gehalten. Einnahmen = `profile.runEarned` plus Wert des vollen Tanks (`Collecting.tankValue`, dieselbe Rechnung wie beim Verkauf). Mindestens `minCrystals` Gewinn, sonst Grund `tooFew`, ohne den Knoten `requires`.
- **`runEarned` (neues Profilfeld, Version 3):** Alle Münzen aus Verkäufen und verkauften Duplikaten laufen über `Wind.credit`, das auf `coins` und `runEarned` bucht. Knotenkäufe senken nur die Münzen. Die Migration schätzt `runEarned` aus den Münzen. `Logic/Wind` ist ein Blatt-Modul (Kristalle, Bonus, Buchung), damit Collecting, Collection und FindRoll es nutzen können, ohne Kreise.
- **Bonus:** `Wind.multiplier` = 1 + Kristalle × `windCrystalBonusBp`/10000. Er ist ein eigener Faktor auf `pricePerSand`, `priceOf`, den Rest ohne Mix und den Fundwert beim Würfeln, multipliziert mit Verkauf-Ast und Sammlungsbonus.
- **Reset:** Zurück gehen `coins`, `tank`, `tankMix`, `runEarned`, alle bekannten gekauften `nodes`, `zones` und `currentZone`. Bleiben: `finds`, `inventory`, `gems`, `receipts`, `pity`, `boosts`, `daily`, `tutorial` und die Zeitstempel. `windCrystals` und `prestiges` steigen. Vergebene Knoten (`sandstorm_1`) werden neu vergeben, auch unbekannte Knoten-IDs gehen zurück (sonst bliebe ein Knoten eines neueren Servers stehen und wirkte gratis). Die Listen stehen in `Sandstorm.RESET_FIELDS`, `UPDATED_FIELDS` und `KEEP_FIELDS`, ein Lune-Test verlangt, dass jedes Feld aus `Profile.default` in genau einer steht.
- **Zonen:** Nach dem Sturm ist nur das Dünenmeer frei (`Zone.unlockNew` auf den neuen Knoten), `currentZone` = erste Zone. Die Ruinenstadt braucht `sandstorm_ruins` (Effekt `zoneKey`, Ast Sandstorm, Spalte 4 im Baum). `ZoneService.resetAfterStorm` setzt den Sammelzustand auf das Dünenmeer und den Charakter an den Spawn.
- **Sicherheit:** `Prestige` hat Schema `{}` und Limit 1 pro 5 s. `Upgrades.onPrestige` rechnet `Sand.settle` ab und ruft `Sandstorm.apply`, das erst alles ausrechnet (auch die Zonen, an einem Schattenprofil) und dann nur noch einfache Zuweisungen ohne Warten schreibt. Ein zweiter schneller Aufruf trifft auf das zurückgesetzte Profil (`requires`). Die Nacharbeit (Sammelzustand, Zone, Meldung, Anzeige) läuft Schritt für Schritt in `pcall` und kippt den gebuchten Sturm nicht; die Antwort an den Client trägt dieselben Werte wie die Meldung, damit die Animation auch bei einer ausgefallenen Meldung läuft. `DataCheck.checkSandstorm` begrenzt die Werte, und keine Zone darf einen vergebenen Knoten verlangen.
- **Studio-Hilfe:** `DebugCoins` hebt auch `runEarned` auf mindestens diesen Wert, so lässt sich der Sturm ohne langen Lauf testen (Knoten `collect_tool_4` kaufen oder per Attribut Münzen setzen).
- **Werte (Balance 2.7, docs/balance/sandstorm_2_7.md):** Einheit 1 Mio., Exponent 0,25, Faktor 4, mindestens 20 Kristalle (etwa 625 Mio. Einnahmen, im ersten Lauf 3,5 min vor dem Baumende), höchstens 100.000 gehaltene Kristalle (das Balance-Dokument nennt es "je Sturm", im Code ist es die Obergrenze der gehaltenen; `Wind.crystalsOf` und `sanitize` kappen kaputte Werte), `sandstorm_ruins` kostet 250 Mio. Ein früher Sturm lohnt sich nie, mit Exponent 0,25 ist das Baumende der beste Zeitpunkt. Der Knopf erscheint ab dem Canyon, vor 20 Kristallen zeigt das Fenster "Noch zu früh" mit den nötigen Einnahmen (`Sandstorm.earningsFor`).
- **Offen für spätere Pakete:** (1) 2x Münzen (4.4) muss in den gebuchten Verkaufsbetrag eingehen, den `Wind.credit` zählt, sonst haben Pass-Käufer weniger Kristalle (erledigt in 4.4: der Münz-Faktor steckt in `Collecting.tankValue` und damit im gebuchten Betrag). (2) Läufe werden mit jedem Sturm kürzer (feste Knotenpreise, linearer Bonus): 6.4 plant einen Ruinen-Ast hinter der Karte oder Sturm-Knoten für Kristalle. (3) Weitere Sturm-Knoten, Sturm-Optik in der Welt (Phase 3), Sounds (3.5).
- **Security-Review 2.7:** Kein kritischer oder hoher Befund (kein Zugriff des Clients auf Kristalle, Münzen oder `runEarned`, keine Doppelauslösung). Eingearbeitet: unbekannte Knoten überleben den Sturm nicht mehr (M1), Nacharbeit je Schritt in `pcall` und Animation auch aus der Antwort (N1), Zonen vor dem Schreiben berechnet (N2), DataCheck verlangt die Startzone als erste Zone (N3), Kristalle beim Lesen und in `sanitize` gekappt (N4), Kommentar zur Fundzeit (N5). Offen für spätere Pakete: (N6) eine Bedingung je vergebenem Knoten, falls es weitere gibt; die Quellen für `runEarned` bei Daily, Offline-Ertrag (5.3), Events und 2x Münzen bewusst festlegen und gekaufte Münzen nie über `Wind.credit` buchen; `Sand.snapshot` rechnet die Vorschau bei jedem Sync (bei Bedarf zwischenspeichern).

## Handy-Durchgang (Paket 3.6)

- **Ziel:** Alle Menüs sind am kleinen Bildschirm bedienbar, die Grafik hat eine schlankere Stufe. Nur der Client ändert sich, Server, Remotes und Profil bleiben unberührt.
- **Größenklasse (`Logic/ScreenLayout`, rein, `tests/screenlayout.spec.luau`):** "compact", wenn die kürzere Bildschirmseite unter `Screen.compactShortSide` (500) liegt, sonst "normal". Aus Klasse, Touch-Flag und Knopfzahl berechnet `ScreenLayout.compute` Rechtecke für HUD-Stapel, Baum-Knopf, Tutorial-Banner, Menü-Knöpfe, Graben-Knopf und die Zone des Sprungknopfs. Ein Lune-Test prüft für viele Größen, dass sich nichts überlappt und alles im Bild liegt. Alle Zahlen stehen in `Data/Screen` (je Klasse) und werden von `DataCheck.checkScreen` geprüft (Tippflächen mindestens 44 px, Grenzen, Grafikstufen).
- **`Controllers/Screen` (Hilfsmodul, lädt seine Oberfläche beim ersten Aufruf):** Besitzt die ScreenGuis "DuneBaronMenu" (DisplayOrder 4, unter dem Baum) und "DuneBaronWindows" (6, über dem Baum, unter Sandwand und Reveal). `addMenuButton(id, text, order)` legt einen Knopf in der Menüleiste an. Unsichtbare Knöpfe nehmen keinen Platz. Am PC steht die Leiste als Reihe unten links, am Handy als Spalte rechts unter "Baum" (mit weiterer Spalte nach links, wenn die Höhe nicht reicht). `createWindow` gibt ein Fenster mit Kopfzeile, Schließen-Knopf (44 px), Reiterstreifen (`sub`), scrollbarem Inhalt (`body` mit UIListLayout) und festem Fuß (`footer`). Die Größe kommt aus `ScreenLayout.windowSize` und folgt der Bildschirmgröße. Es ist immer nur ein Fenster offen (Öffnen schließt die anderen), der Baum schließt alle. `layout()`, `classData()` und `onLayoutChanged` geben HUD, Tutorial, Reveal, Graben-Knopf und Debug-Anzeige ihre Plätze. Wer später einen Knopf braucht (Gems, Shop in 4.1/4.5), ruft nur `addMenuButton` und `createWindow` auf.
- **Eingabe am Handy:** `Input` bindet die Sammel-Aktion ohne Standard-Knopf und zeigt stattdessen einen runden Knopf "Graben" links neben dem Sprungknopf (Platz aus dem Layout). Er folgt dem Finger, der ihn hält, und endet bei Loslassen irgendwo, Abbruch und Fensterwechsel. Im Baum ist er weg.
- **Baum (`Data/TreeLayout`, `Logic/TreeCamera`):** `zoom.startCompact` (0,8) lässt den Baum am kleinen Bildschirm mit mehr Überblick starten (`TreeCamera.startZoom`), `tapMaxMovePixelsTouch` (14) ist die Tipp-Toleranz für Finger (`TreeCamera.isTap(moved, nil, touch)`). Die Karte hat zwei Zeilen Beschreibung. Der Knopf "Baum" liest Größe und Platz aus dem Layout.
- **Grafikstufen (`Logic/GraphicsLevel`, `Controllers/Graphics`, Daten in `Data/Screen.graphics`):** "hoch" (PC), "schlank" (Touch-Gerät oder Grafikregler 1 bis 3), "minimal" (Rückfall des Bildraten-Wächters, auch am PC). Ein Spieler-Attribut `GraphicsLevel` erzwingt eine Stufe zum Testen (nil = automatisch). Schlank schaltet Bloom, Sonnenstrahlen, Tiefenschärfe und Unschärfe im Lighting nur auf diesem Client ab (der Ursprungszustand wird gemerkt), halbiert Partikel (Wetter, Sandfluss, Staub), lässt fremde Werkzeuge ohne Schatten und nur bis 40 % der Bewegungsentfernung laufen und lässt das Licht am Fund-Objekt weg. Minimal schaltet zusätzlich Sandfluss, Wetter-Partikel und Reveal-Effekte aus. Die Terrain-Verformung bleibt in "schlank" an. `Dig` meldet den Rückfall über `Graphics.setFallbackProvider`, damit sich die Module nicht gegenseitig laden. Die Debug-Anzeige zeigt die Stufe.
- **Nicht in diesem Paket:** Hochformat-Feinschliff über Layout-Tests hinaus, ein Einstellungsfenster für die Grafik, echte Icons (3.1) und der Look (3.4). `Lighting.Technology` ändert sich zur Laufzeit nicht, die Future-Beleuchtung regelt Roblox am Handy selbst.

## Kaufabwicklung (Paket 4.1)

- **Grundsatz:** `PurchaseGranted` gibt es erst, wenn die PurchaseId nachweislich im gespeicherten Spielstand steht (ProfileStore `profile.LastSavedData`, gemeldet über `OnAfterSave`). Sonst `NotProcessedYet`, und Roblox ruft den Beleg später erneut auf (auch auf einem anderen Server). Vom Beleg zählen nur `PlayerId`, `ProductId` und `PurchaseId`. Menge und Preis kommen aus `GemPacks` bzw. `Products`, kein Wert vom Client geht in einen Kauf ein, es gibt keine neue Remote.
- **Module:** `Logic/Purchases` (rein, Lune-Tests in `tests/purchases.spec.luau`) bekommt alles als Adapter: `getProfile`, `isSessionActive`, `isLoading`, `saveAndWait`, `now`, `clock`, `wait`, `log`, `notify`, `handlers`, `allowDebug`, `data` (nur Tests). `Logic/Gems` (rein, `tests/gems.spec.luau`): `grant` (nur ganze Zahlen über 0, kappt bei `maxGems`, gibt die gebuchte Menge zurück), `spend` (`notEnoughGems`, `invalidAmount`), `canAfford`, `balance`. Jede Buchung nennt ihre Quelle als Text. `Services/Shop` setzt `MarketplaceService.ProcessReceipt` genau einmal und schließt PlayerData, Uhr, `Notify` und `Sand.refresh` an.
- **Speicher-Adapter:** Die Sitzung aus `PlayerSession` kennt zusätzlich `save` (`profile:Save()`), `lastSaved` (`profile.LastSavedData`), `isActive` (`profile:IsActive()`) und `onAfterSave` (`profile.OnAfterSave`). Der Manager bietet `isActive(userId)`, `isSaved(userId, bedingung)` und `saveAndWait(userId, bedingung, sekunden)`: Erfüllt der zuletzt gespeicherte Stand die Bedingung schon, wird nicht erneut gespeichert, sonst speichern und warten (Abfrage alle 0,1 s über die eingespeiste Funktion `wait`, im Spiel `task.wait`; bestätigt wird über `OnAfterSave` oder einen neuen `LastSavedData`). Endet die Sitzung während des Wartens, wird bis zur Zeitgrenze weiter gewartet: ProfileStore setzt beim Beenden zuerst `IsActive` auf false und schreibt erst danach ein letztes Mal (`OnAfterSave`). Nur der gespeicherte Stand zählt. Beim Laden werden `receipts` und `purchaseLog` nicht gekürzt (`Profile.sanitize(profil, jetzt, { trimLists = false })`), erst beim nächsten Speichern. `PlayerData` reicht das als `getByUserId`, `isActive` und `saveAndWait` weiter. Die Bedingung des Shops ist `Purchases.hasReceipt(gespeicherterStand, purchaseId)`.
- **Ablauf je Beleg:**
  1. Beleg prüfen: PlayerId ganze Zahl ungleich 0, PurchaseId nicht leerer Text (höchstens 128 Zeichen), ProductId ganze Zahl über 0.
  2. Produkt über die ProductId nachschlagen (Gem-Pakete und Produkte außer Gamepasses mit ProductId über 0). Platzhalter 0, unbekannt, doppelt vergeben oder ohne Handler: ein Protokolleintrag, `NotProcessedYet`.
  3. Sperre je Spieler und PurchaseId: Ein gleichzeitiger zweiter Aufruf wartet auf das Ergebnis des ersten und bucht nie selbst. Seine Grenze (`PROFILE_WAIT_SECONDS` + `saveTimeoutSeconds` + 5 s = 165 s) ist mindestens so lang, wie der erste höchstens braucht, er gibt also nie vor ihm auf.
  4. Profil holen. Lädt es noch und der Spieler ist da, wartet der Kauf höchstens `PROFILE_WAIT_SECONDS` = 130 s darauf (mindestens `LOAD_TIMEOUT_SECONDS` = 120 s aus PlayerData plus Puffer; ein Test liest beide Werte; Roblox schickt offene Belege gleich beim Beitreten). Kein Profil, Spieler weg oder Sitzung nicht aktiv: `NotProcessedYet`, keine Gutschrift.
  5. Steht die PurchaseId schon in `profile.receipts`: keine Gutschrift, nur noch auf das bestätigte Speichern warten.
  6. Sonst zuerst alles ausrechnen, im kritischen Fenster: Vom Kopieren des Profils über Handler (auf Kopien von Profil und Produkt), Prüfung, Uhr (`now`), Protokoll (`log`) bis zur erneuten Prüfung läuft alles in einer eigenen Koroutine; wartet darin irgendetwas (yield), wird sie geschlossen (`coroutine.close`), nichts geschrieben, `NotProcessedYet`. Seine Antwort wird geprüft (siehe Handler-Register). Dazu neue Beleg-Liste (PurchaseId ans Ende, über `receiptCacheSize` fliegt die älteste raus), Protokolleintrag (höchstens `purchaseLogSize`) und `spent`. Ein Kappen-Hinweis kommt vor dem Schreiben ins Protokoll. Direkt vor dem Schreiben erneut prüfen: `getProfile` liefert noch dasselbe Profil, Sitzung aktiv, PurchaseId noch nicht da; sonst `NotProcessedYet`. Dann schreibt Purchases selbst, alles oder nichts: die Felder aus `changes` (sortiert), dann `receipts`, `purchaseLog`, `spent`. Wirft eine Zuweisung, werden alle Felder auf den Stand davor gesetzt, es bleibt weder Teilware noch PurchaseId. Das Schreiben folgt direkt nach der Koroutine im selben Thread und weist nur zu, es wartet nie. So kann sich das Profil zwischen Kopie und Schreiben nicht ändern.
  7. `saveAndWait` (höchstens `saveTimeoutSeconds`). Bestätigt: Meldung an den Client (`Notify { kind = "gemsBought", gems, total, productId }`, in einer eigenen Koroutine; wartet sie, wird sie geschlossen, damit die Sperre nie hängt), `Sand.refresh`, `PurchaseGranted`. Sonst `NotProcessedYet`. Gemerkt wird je Kauf nur die Meldefunktion; endet ein Aufruf mit `NotProcessedYet` und der Spieler ist nicht mehr da, wird sie vergessen.
  Alles läuft in `pcall`, ein Fehler ergibt `NotProcessedYet` und einen Eintrag im Output (`[Shop]`).
- **Fehlerfälle:** Speichern schlägt fehl oder läuft in die Zeitgrenze: `NotProcessedYet`, Gems und PurchaseId bleiben gemeinsam im Profil; der nächste Aufruf bucht nicht neu und gibt `PurchaseGranted`, sobald ein Speichern sie bestätigt (dann kommt auch die Meldung, einmal je Server). Absturz vor dem Speichern: beides ist verloren, der nächste Server bucht genau einmal. Absturz nach dem Speichern, aber vor der Antwort: der nächste Server findet die PurchaseId und bucht nicht neu. Sitzung endet während des Wartens (Verlassen, anderer Server, Absturz): es wird bis zur Zeitgrenze weiter gewartet; enthält das letzte Speichern den Kauf, gibt es `PurchaseGranted`, sonst `NotProcessedYet` und der nächste Server bucht genau einmal. Bei `maxGems` gekappt: Der Kauf gilt (sonst käme der Beleg ewig wieder), das Protokoll nennt die tatsächlich gutgeschriebene Menge, der Output warnt. Eine fehlschlagende Meldung ändert nichts am bestätigten Kauf.
- **Handler-Register (für 4.4):** Gem-Pakete sind eingebaut. `Shop.registerProduct(produktId, handler)` hängt ein Produkt aus `Data/Products` ein (nur Developer Products, nicht Gamepasses), in `Init` oder `Start`. Ein Handler `(profilKopie, produktKopie, data) -> Prepared?` darf nie warten und gibt `{ changes, gems, announce? }` zurück: `changes` sind neue Werte für oberste Profilfelder (zum Beispiel `{ boosts = neueTabelle }`), Purchases weist sie selbst zu. Abgelehnt (`NotProcessedYet`, ein Protokolleintrag) werden: keine Tabelle, `changes` fehlt, `gems` keine ganze Zahl ab 0, `announce` keine Funktion, Schlüssel kein Text, die Felder `receipts`, `purchaseLog`, `spent`, `version`, nicht speicherbare Werte (Funktionen, NaN, unendlich, gemischte oder lückenhafte Tabellen) und Werte, die nicht zum Profil-Schema passen: `changes.gems` ganze Zahl von 0 bis `maxGems`; die Änderungen werden auf eine Kopie gelegt und `Profile.sanitize` läuft darüber, ändert es ein geändertes Feld (falscher Typ, kaputter Zahlentyp `{m, e}`, negativ, gebrochen), wird abgelehnt statt beim Speichern still repariert. `announce(profilKopie)` liefert Art und Daten der Meldung nach dem bestätigten Speichern. Unbekannte Produkte und doppelte Handler sind ein Fehler beim Registrieren. Nach allen `Start()` ruft der Server-Bootstrap `Shop.AfterStart`: Hat ein Produkt mit ProductId über 0 (kein Gamepass) keinen Handler (`Purchases.missingHandlers()`), meldet der Server das laut im Output (Warnung), läuft aber weiter. Eine ProductId trägt man erst ein, wenn ihr Handler existiert.
- **Profil Version 4:** `receipts` ist eine Liste der PurchaseIds (neueste am Ende), `purchaseLog` eine Liste `{ purchaseId, productId, gems, robux, time }` (`productId` ist die ID aus den Daten, zum Beispiel `gems_550`), `spent = { robux, count }`. `Migrations.steps[3]` übernimmt die Schlüssel der alten Tabelle `{ [id] = true }` sortiert (jeder speicherbare Wert außer `false` zählt als Beleg). `Profile.sanitize`: Gems ganz, ab 0, höchstens `maxGems`; `receipts` und `purchaseLog` lückenlose Listen ohne Textschlüssel (der DataStore speichert keine gemischten Tabellen), vor dem Speichern gekürzt auf die Größen aus `Economy.purchases` (beim Laden nicht: aus der alten Tabellenform ist die Reihenfolge unbekannt, Kürzen würde beliebige PurchaseIds entfernen; bis zum ersten Speichern stehen alle auch im zuletzt gespeicherten Stand); ist `receipts` gar keine Tabelle, kommen die PurchaseIds aus dem Kaufprotokoll zurück; `spent` ganz und nicht negativ. `Profile.receiptList` und `Purchases.hasReceipt` verstehen beide Formen. Der Sandsturm behält `gems`, `receipts`, `purchaseLog` und `spent`.
- **Werte:** `Economy.purchases = { receiptCacheSize = 100, purchaseLogSize = 50, saveTimeoutSeconds = 30, maxGems = 10_000_000 }`. `DataCheck` verlangt ganze Zahlen in den Bereichen 50 bis 1000 (`receiptCacheSize`), 1 bis 500 (`purchaseLogSize`), 1 bis 120 (`saveTimeoutSeconds`) und 10^6 bis 10^9 (`maxGems`: nie senken, sonst kappt `sanitize` bezahlte Guthaben), `receiptCacheSize` mindestens `purchaseLogSize`, kein Gem-Paket über `maxGems`, keine doppelte ProductId (außer 0) und keine Produkt-ID (`id`), die in `GemPacks` und `Products` zugleich steht. Gamepasses und Developer Products haben bei Roblox getrennte Nummernkreise und werden getrennt geprüft.
- **Studio-Hilfe:** Nur in Studio (`RunService:IsStudio()`): In der Befehlszeile (Ansicht Server) `game.Players.<Name>:SetAttribute("DebugPurchase", "gems_550")` (neue zufällige PurchaseId) oder `"gems_550:fest1"` (feste PurchaseId, für den Doppelkauf-Test). Der Shop löscht das Attribut sofort wieder, damit derselbe Wert erneut auslöst, und ruft `Purchases.processPack(userId, paketId, purchaseId)`: das Paket kommt über die Paket-ID (die ProductIds sind noch 0), die PurchaseId bekommt das Präfix `studio:`, danach läuft derselbe Ablauf wie bei einem echten Beleg. Außerhalb von Studio ist der Weg doppelt gesperrt: kein Attribut-Listener und `allowDebug = false` in `Purchases`. Der Echtpfad lehnt ProductId 0 immer ab.
- **Bekannte Grenzen:** Eine PurchaseId, die nach mehr als `receiptCacheSize` späteren Käufen aus der Liste gefallen ist, gälte bei einem erneuten Beleg als neu (Roblox wiederholt nur unbestätigte Belege, darum praktisch ausgeschlossen). Mehrere Käufe kurz nacheinander speichern hintereinander (DataStore-Grenze je Schlüssel etwa alle 6 s), die Zeitgrenze von 30 s reicht dafür. Hat ein altes Profil mehr PurchaseIds in Tabellenform als `receiptCacheSize`, kürzt das erste Speichern nach dem Laden alphabetisch; ein Beleg, den Roblox erst danach wiederholt, gälte als neu (alte Spielstände haben praktisch keine Belege, vor 4.1 gab es keine Käufe). Das Zusammenspiel mit dem echten ProfileStore (`OnAfterSave` auch beim letzten Speichern, `LastSavedData`, Sitzungsübernahme) und das Abbrechen eines Handlers, der `task.wait` aufruft, sind nur in Studio prüfbar.

## Kisten (Paket 4.2)

- **Grundsatz:** Der Client schickt nur `OpenCrate(crateId, count)` (Schema und Limit aus `RemoteSpec`: Kiste aus `Crates`, Anzahl 1 oder 10, 1 Aufruf pro s). Preis, Würfe, Pity und Gewinne bestimmt allein der Server aus `Data/Crates` und `Data/CrateItems`. Es gibt keine neue Remote. Quoten sind Hundertstel-Prozent (10000 = 100 %).
- **Eine Tabelle für Anzeige und Auswurf (`Logic/CrateRoll`, rein):** `CrateRoll.oddsOf(crate)` ist der einzige Zugriff auf die Quoten. `displayOdds(crateId)` (Kisten-Fenster: alle sechs Seltenheiten nach Rang mit der Zahl aus der Tabelle, `odds` ist dieselbe Referenz wie `Crates.byId[id].odds`, dazu die Pity-Grenzen) und `roll` lesen darüber. Die Event-Kiste verweist auf die Tabelle der Goldkiste. Der Kisten-Client liest `Crates.byId[id].odds` direkt, also dieselbe Tabelle.
- **Wurf:** Der Zufall kommt als `random() -> [0, 1)` herein (im Spiel ein `Random.new()` je Server). Seltenheit: Los = floor(r × Summe) + 1, also 1 bis 10000. Die Seltenheiten belegen in Rang-Reihenfolge Bereiche so breit wie ihre Quote, Quote 0 kommt nie vor. Danach ein Item gleich verteilt aus dem Pool der Kiste mit dieser Seltenheit (Reihenfolge wie in `CrateItems.list`). Ein Zufallswert außerhalb von [0, 1) oder ein leerer Pool ist ein Fehler, nie ein stiller Wurf.
- **Pity:** Gold- und Event-Kiste haben je `pity = { epic = 15, legendary = 60 }` in den Daten und eigene Zähler `profile.pity.gold` und `profile.pity.event` (`{ sinceEpic, sinceLegendary }`). Bei `sinceLegendary >= legendary - 1` wird nur unter Legendär und Mythisch gewürfelt (450:50), sonst bei `sinceEpic >= epic - 1` nur unter Episch und besser (1500:450:50). Greifen beide, gewinnt Legendär. Danach: Legendär oder Mythisch setzt beide Zähler auf 0, Episch nur `sinceEpic` (`sinceLegendary` zählt weiter), alles darunter zählt beide hoch. Holz und Eisen haben keine Pity und ändern keinen Zähler. Raten mit Pity (exakt, `docs/balance/crates_4_2.md`, im Lune-Test nachgerechnet): Legendär oder besser 5,387 %, Episch oder besser 20,882 %, Mythisch 0,539 %.
- **Öffnen (`Logic/CrateOpen`, rein):** Die erste nicht erfüllte Bedingung ist der Grund: `unknownCrate`, `badCount` (nur 1 oder `bundle.buy`), `restricted` (`restricted ~= false`, also auch unbekannt; gilt für alle Kisten, auch die Holzkiste), `notInSeason` (Event-Kiste ohne `inSeason == true`; der Service setzt bis zum Saison-Kalender in 5.x immer `false`), `noProfile`, dann der Preis: einzeln `price`, 10er-Paket `price × bundle.buy`; Holzkiste in Münzen (Zahlentyp, `notEnoughCoins`), Eisen, Gold und Event in Gems über `Gems.spend` (`notEnoughGems`, die einzige Gem-Abbuchung). Geöffnet wird einmal bzw. `bundle.get` (11) Mal nacheinander, jede Öffnung zählt für die Pity. Gewinne zählen im Inventar hoch (`inventory.skins`, `companions`, `toolVariants` nach `kind`), `isNew` ist false, wenn das Item vorher schon da war (auch innerhalb eines Pakets).
- **Kein halbes Buchen:** Alles wird auf Arbeitskopien (Gems bzw. Münzen, Pity, Inventar) in einer eigenen Koroutine gerechnet. Wirft sie (zum Beispiel ein kaputter Zufall) oder wartet sie (yield), wird sie geschlossen und nichts geschrieben: Grund `error`, Profil unverändert. Danach weist derselbe Thread nur noch fertige Werte zu (`gems` bzw. `coins`, `pity`, `inventory`). Im Block gibt es keinen DataStore-, Policy- oder Netzaufruf; gespeichert wird über das normale Autosave von ProfileStore. Ein Absturz vor dem Speichern verliert Bezahlung und Gewinn gemeinsam.
- **Antwort an den Client:** `{ ok = true, crateId, count, results = { { itemId, kind, rarityId, name, isNew, pityTriggered } }, highest, pity, gems, coins, free }` oder `{ ok = false, reason }`. Gründe des Service zusätzlich: `busy` (eine Öffnung desselben Spielers läuft noch; kann heute nicht vorkommen, weil der Block nie wartet, schützt gegen spätere Änderungen) und `error` (Fehler im Handler). Der Fehlertext (`detail`) geht nur ins Server-Protokoll (`[Crates]`). Nach Erfolg sendet `Sand.refresh` den neuen Zustand (Gems, Münzen, Pity). Eine eigene Meldung (`Notify`) gibt es nicht, das Reveal läuft aus der Antwort.
- **Gratis-Öffnung:** `CrateOpen.openFree(profil, kistenId, ctx)` für den Daily Reward (5.1): eine Öffnung, keine Abbuchung, zählt für die Pity. Policy und Saison gelten genauso; bei gesperrter Policy gibt 5.1 den festen Ersatzgegenstand. Angeschlossen über `ClaimDaily` (Tag 7, `Logic/Daily` ruft es auf einer Arbeitskopie des Profils auf, siehe "Daily Reward (Paket 5.1)").
- **Policy-Cache (`Logic/PolicyCache`, rein; Service `Crates`):** Beim Beitreten (`PlayerAdded` und schon anwesende Spieler) holt ein eigener Thread `PolicyService:GetPolicyInfoForPlayerAsync(player)`, höchstens `POLICY_ATTEMPTS` = 3 Versuche in `pcall`, dazwischen `POLICY_RETRY_SECONDS` = 2 s. Nur eine Tabelle mit `ArePaidRandomItemsRestricted` als true/false zählt. Bis dahin und nach drei gescheiterten Versuchen gilt der Spieler als gesperrt (fail-closed): jede Öffnung endet mit `restricted`, `cratesAllowed` ist false. In derselben Sitzung wird nicht erneut gefragt, ein Rejoin fragt neu. `PlayerRemoving` vergisst den Wert, und ein alter Abruf, der erst nach dem Verlassen oder nach einem schnellen Rejoin fertig wird, schreibt nichts. Steht das Ergebnis eines noch gültigen Abrufs fest (erlaubt, gesperrt oder nach drei Fehlschlägen unbekannt), schickt der Service den Zustand neu (`Sand.refresh`).
- **Studio-Hilfe:** Nur in Studio überschreibt das Spieler-Attribut `DebugCratesRestricted` (true/false, nil = echte Policy) den Cache: `game.Players.<Name>:SetAttribute("DebugCratesRestricted", true)` in der Befehlszeile (Ansicht Server). Der Zustand wird danach neu gesendet. Außerhalb von Studio wird das Attribut nie gelesen.
- **Schnittstelle zu Sand:** `Sand.addSnapshotProvider(fn)` hängt Felder an den StateSync, ohne dass Sand den Crates-Service lädt. Crates liefert `{ cratesAllowed = Crates.isAllowed(player) }` (true nur bei bekannter, nicht sperrender Policy). `Sand.snapshot` schickt außerdem `pity` (Kopie je Kiste). `Crates.isAllowed(player)` ist für andere Services exportiert (zum Beispiel Daily Reward in 5.1).
- **Profil:** `pity.event` steht neu in `Profile.default`; alte Spielstände bekommen es über `Profile.migrate` (fehlende Felder werden aufgefüllt, keine Migration, die Version bleibt). `Profile.sanitize` repariert die Zähler: ganze Zahlen ab 0, Brüche abgerundet, bei Kisten mit Pity gekappt auf Grenze − 1 (dort greift die Garantie ohnehin), Einträge ohne Tabelle entfernt, unbekannte Kisten-IDs bleiben. Der Sandsturm behält `pity` und `inventory`.
- **DataCheck:** Jede Quotentabelle ergibt 10000; Pity der Gold- und der Event-Kiste 15/60; jede Pity hat ganze Grenzen ab 1, `epic` nicht über `legendary`, und ihre Garantie ist erreichbar (eine Seltenheit ab dieser Stufe hat Quote über 0). `CrateItems`: eindeutige IDs, `kind` skin/companion/toolVariant, Name, bekannte Seltenheit, mindestens eine bekannte Kiste ohne Doppelte, Event-Items nur in `event`, `effectBp` = 0 (Wirkungen in 4.3), kein Item, das in seiner Kiste nie fallen kann (Quote 0), und jede Seltenheit mit Quote über 0 hat in jeder Kiste mindestens ein Item (ein Lune-Test verlangt für die echten Daten das Soll von 3).
- **Tests:** `tests/crateroll.spec.luau` (Simulation 200.000 Öffnungen je Kiste ohne Pity, Pity-Simulation Gold gegen die exakte Markov-Kette und den Wert des balance-analyst, feste Zufallsfolgen), `tests/crateopen.spec.luau` (Bezahlen, Sperren, Event, Fehler und Warten ohne Buchung, Inventar, Gratis-Öffnung, Speichern und Laden, Sandsturm), `tests/policycache.spec.luau` (Versuche, fail-closed, Rejoin), `tests/data.spec.luau` (DataCheck). Die Läufe dauern zusammen etwa 2,5 s.
- **Bekannte Grenzen:** Die Policy wird einmal je Sitzung geholt; ändert Roblox sie während der Sitzung, gilt das erst nach dem Rejoin. Scheitern alle drei Versuche, bleiben Kisten bis zum Rejoin gesperrt (gewollt, fail-closed). Echtes Verhalten von `PolicyService` (Antwortzeit, Fehler, Studio-Werte) und das Zusammenspiel mit dem Kisten-Fenster sind nur in Studio prüfbar.

## Kisten-Items: Ausrüstung und Verschmelzen (Paket 4.3)

- **Grundsatz:** Kisten-Items wirken auf die Sammelrate, sonst auf nichts (Konzept: keine Änderung der Kisten- und Fundquoten, kein Verkauf, kein Tausch). Drei Slots, je einer pro Art (`skin`, `companion`, `toolVariant`); nur ausgerüstete Items wirken. Die Regeln stehen im reinen Modul `Logic/Equipment` (Lune-Tests `tests/equipment.spec.luau`), der Service `Equipment` hängt nur Remotes, Profil und Anzeige daran.
- **Rechnung:** `Collecting.rateOf = Werkzeug × (1 + Baum) × (1 + Summe der Item-Boni)`, die Item-Boni sind ein eigener Faktor (nicht in der Baum-Summe). Bonus eines Items = `floor(effectBp × (10000 + (Sterne − 1) × starBonusBp) / 10000)`. `effectBp` steht in `Data/CrateItems` (nach Seltenheit: Gewöhnlich 500, Ungewöhnlich 700, Selten 1000, Episch 1400, Legendär 1900, Mythisch 2500, jeweils ★1), die Sternregeln in `Economy.items` (`maxStars` 5, `starBonusBp` 1500, `copiesToMerge` { 1, 2, 3, 4 }, `maxEffectBp` 2500, `maxTotalBonusBp` 12000). ★5 ist also das 1,6-fache. Das Maximum (drei Mythische ★5) liegt bei +120 %; `Equipment.bonusBp` deckelt die Summe bei `maxTotalBonusBp`, und DataCheck verlangt, dass drei Items mit höchstem Wert und Stern den Deckel nicht überschreiten (schützt vor Tippfehlern in den Tabellen). Werte und Prüfung: `docs/balance/equipment_4_3.md`.
- **Verschmelzen:** Der Schritt auf ★n verbraucht `copiesToMerge[n − 1]` Kopien desselben Items, ein Exemplar bleibt immer (für ★5 braucht man insgesamt 11 Exemplare). Kein Zufall, keine Kosten, kein Verkauf. Ein ausgerüstetes Item bleibt ausgerüstet, der höhere Bonus gilt sofort. Auf ★5 wird abgelehnt (`maxStars`).
- **Spielstand (Version 5):** `profile.equipped = { skin, companion, toolVariant }` (Item-ID oder `""`) und `profile.itemStars = { [itemId] = 2..maxStars }` (fehlt = ★1). Besitz bleibt `profile.inventory` (Anzahl Exemplare). Migration 4 → 5 legt beide Felder an. `Profile.sanitize` leert Slots mit unbekanntem, falsch eingeordnetem oder nicht besessenem Item, kappt Sterne auf 2 bis `maxStars`, entfernt Ungültiges; unbekannte Item-IDs in `itemStars` bleiben (wirken nicht). Der Sandsturm behält beide Felder wie das Inventar. Ein kaputter oder veralteter Eintrag wirkt nie: `Equipment.equippedItem` prüft bei jedem Zugriff Bekanntheit, Art und Besitz.
- **Remotes:** `EquipItem(slot, itemId)` (2 je Sekunde, jede Änderung baut die Optik aller Clients neu; Slot aus `Equipment.SLOTS`, itemId als Text bis 64 Zeichen, `""` nimmt ab) und `MergeItem(itemId)` (2 je Sekunde; ID aus `CrateItems`). Antwort `{ ok, reason?, itemId?, stars?, copies?, consumed?, bonusBp? }`. Gründe: `badSlot`, `unknownItem`, `wrongSlot`, `notOwned`, `notEnoughCopies`, `maxStars`, `noProfile`, `error`. Der Server prüft alles zuerst und schreibt erst danach in einem Zug ohne Warten, jede Ablehnung lässt das Profil unverändert. Vor der Änderung rechnet `Sand.settle` das offene Sammelfenster mit der alten Rate ab (scheitert das, wird abgebrochen). Ein Ausrüsten ohne Änderung (`changed = false`) sendet keinen neuen Zustand.
- **Anzeige für alle:** `Sand.publishLook` setzt die Spieler-Attribute `SkinId`, `CompanionId`, `ToolVariantId` (nur aus gültiger Ausrüstung, der Client kann sie für andere nicht ändern). Der StateSync bekommt über `Sand.addSnapshotProvider` `inventory`, `equipped`, `itemStars`, `equipBonusBp` (Kopien). Client: `ItemVisual` baut aus `Data/ItemLooks` Umhang mit Schärpe und den schwebenden Begleiter (einfache Formen, nicht abfragbar, weit entfernte Spieler seltener aktualisiert), `ToolVisual` färbt das Werkzeug mit der Variante um, `EquipmentMenu` ist das Fenster "Ausrüstung" (Menüleiste Platz 6, drei Reiter, Karten mit Bonus, Sternen, Kopien, Knöpfen). Der Kisten-Reveal zeigt den Bonus und bei einem Duplikat den Fortschritt zum nächsten Stern.
- **Policy:** Ausrüsten und Verschmelzen bleiben bei `ArePaidRandomItemsRestricted = true` erlaubt: Sie kaufen und würfeln nichts. Der Ersatzgegenstand der Daily Reward (5.1) braucht dieses Fenster.
- **Studio-Hilfe:** Nur in Studio legt `game.Players.<Name>:SetAttribute("DebugItem", "skin_common_1:5")` Exemplare ins Inventar (ohne Zahl: 1, höchstens 50 je Aufruf); Befehlszeile Ansicht "Server". Das Attribut wird danach zurückgesetzt. Außerhalb von Studio wird es nie gelesen.
- **DataCheck:** `effectBp` ganze Zahl von 0 bis `Economy.items.maxEffectBp`; Sternregeln gültig (`maxStars` 2 bis 10, `copiesToMerge` genau `maxStars − 1` ganze Zahlen ab 1); jedes Item hat in `Data/ItemLooks` genau ein Aussehen mit gleicher Art, gültigen Hex-Farben, Material und bei Begleitern Form (Ball/Block) und Größe 0,8 bis 2,2; kein Aussehen ohne Item.
- **Bekannte Grenzen:** Die Optik (Umhang, Begleiter, Werkzeugfarbe) sind Platzhalter bis Paket 3.2 und nur in Studio prüfbar. Der Offline-Ertrag des Begleiters kommt mit 5.3 und nutzt `Collecting.rateOf`. Die Holzkiste (25.000 Münzen) wird im Spätspiel billig; die Items dort sind höchstens Episch, die Wirkung ist gedeckelt (siehe Balance-Dokument).

## Gamepasses und Münz-Boost (Paket 4.4)

- **Grundsatz:** Der Server entscheidet Besitz und Wirkung. Der Client schickt nur `SetAutoDig(enabled)` (Schalter); Gamepass-Käufe meldet `PromptGamePassPurchaseFinished`, zählen aber erst nach einer Bestätigung durch `UserOwnsGamePassAsync` (das Ereignis kann ein Exploit fälschen), der Münz-Boost läuft über ProcessReceipt wie die Gem-Pakete. Regeln in den reinen Modulen `Logic/Passes` (Besitz) und `Logic/Perks` (Wirkungen, Boost, Auto-Dig, Kauf-Handler), Lune-Tests in `tests/passes.spec.luau` und `tests/perks.spec.luau`. Der Service `Passes` (zwischen Equipment und Shop in `SERVICE_NAMES`) schließt MarketplaceService, PlayerData, Sand und Shop an.
- **Daten:** Jeder Gamepass in `Data/Products` hat `perk` (`double_coins` → `doubleCoins`, `auto_dig` → `autoDig`, `big_tank` → `bigTank`). Der Code kennt Wirkungen nur über `perk` (`Perks.PERK_IDS`), nie über Produkt-IDs; die Produkt-ID ist nur der Schlüssel in `profile.passes` und darf nie umbenannt werden. Der Kopf von `Data/Products` warnt (Security-Review 4.4): eine eingetragene Gamepass-ID nie ändern (alte Käufer bekämen "nein" und verlören den Pass), keinen Pass verkaufen, solange seine ID 0 ist, und nie einen Pass aus der Liste löschen (sanitize würde ihn aus allen Profilen entfernen). `Economy.doubleCoinsMultiplier = 2` (neu), `Economy.bigTankMultiplier = 2`, `Economy.coinBoost = { durationSeconds = 1800, multiplier = 2 }`.
- **Spielstand (Version 6):** `profile.passes = { [passId] = true }` (gemerkter Besitz, nur der Server schreibt) und `profile.settings = { autoDig = true }`. `Migrations.steps[5]` legt nur Fehlendes an (vorhandener Besitz bleibt, auch wenn die Kette bei einem kaputten Versionsfeld erneut läuft). `Profile.sanitize`: `passes` behält nur bekannte Gamepass-IDs mit Wert `true` (ein Pass eines neueren Servers wird entfernt und dort von der Abfrage wieder eingetragen), `settings.autoDig` Boolean (sonst an), `boosts.coinsUntil` endlich und ab 0 (NaN, unendlich und negativ werden 0). Der Sandsturm behält `passes`, `settings` und `boosts` (`Sandstorm.KEEP_FIELDS`).
- **Besitz (`Logic/Passes`, `Services/Passes`):**
  - Beim Laden prüft je Gamepass mit `productId > 0` ein eigener Thread den Besitz (`Passes.runCheck`): je Runde `UserOwnsGamePassAsync` in `pcall` (`CHECK_ATTEMPTS` = 3 Versuche, `CHECK_PAUSE_SECONDS` = 2 s dazwischen; `Passes.ask`), Runden im Abstand `RECHECK_SECONDS` = 60 s, höchstens `CHECK_ROUNDS` = 10, solange der Spieler mit demselben Profil da ist. Nur eine Antwort true/false zählt. "Ja" trägt sofort ein. "Nein" entfernt erst, wenn auch die nächste Runde "nein" sagt (`Passes.decideCheck` gibt beim ersten "nein" `confirmNo`); ein Fehler dazwischen behält den Pass und die Zählung beginnt neu (Security-Review 4.4: ein einzelnes veraltetes "nein" nimmt nichts weg). Ein "nein" entfernt nie in Studio (Testkäufe zählen bei Roblox nicht als Besitz) und nie einen Pass, der in dieser Sitzung gekauft und bestätigt wurde (der Kontext wird je Runde live gelesen). Scheitert die Abfrage, bleibt der gemerkte Besitz. ProductId 0: keine Abfrage, nur der gemerkte Besitz.
  - `PromptGamePassPurchaseFinished` trägt nie selbst etwas ein (`Passes.newPurchaseConfirmer`). Bei einer ganzen Gamepass-ID über 0, die zu genau einem Gamepass gehört (doppelt vergebene IDs werden nie geraten), startet ein eigener Thread eine Abfrage `UserOwnsGamePassAsync(player.UserId, gamePassId)`, egal was `wasPurchased` sagt: bei `wasPurchased == true` bis zu `CONFIRM_ROUNDS` = 3 Runden im Abstand `CONFIRM_RETRY_SECONDS` = 10 s (falls Roblox den Kauf noch nicht kennt), sonst eine Runde. Nur bei "ja" und wenn der Spieler danach noch da ist, wird der Pass als "in dieser Sitzung gekauft" gemerkt und über `Passes.decideConfirmedPurchase` in das dann aktuelle Profil geschrieben. Je Spieler und Pass läuft höchstens eine Prüfung (weitere Ereignisse: `busy`; ein Ereignis mit `wasPurchased == true` verlängert eine laufende Ein-Runden-Prüfung auf alle Runden, damit ein Kauf direkt nach einem abgebrochenen Kauffenster nicht verloren geht), ein schon eingetragener Pass wird nicht abgefragt (`owned`), unbekannte IDs starten nichts und werden je Spieler nur einmal gemeldet. Ist das Profil noch nicht geladen, wird der Kauf erst nach der Bestätigung gemerkt und `Passes.withBought` trägt ihn beim Laden ein. Für abwesende Spieler wird nichts gemerkt, `PlayerRemoving` räumt Merker, Drossel und laufende Prüfungen auf. Nur in Studio (`trustEvent`) gilt `wasPurchased == true` ohne Abfrage, weil Studio-Testkäufe bei Roblox nie als Besitz zählen.
  - Jede Änderung: `Sand.settle` (altes Fenster mit altem Tank, ein Fehler dabei wird gemeldet, verhindert die Änderung aber nicht), dann ohne Warten `profile.passes` als neue Tabelle, dann `Sand.refresh`. Entscheidungen geben neue Tabellen zurück oder nil (keine Änderung, kein Schreiben).
- **Wirkungen (`Logic/Perks`):** `Perks.options(profile, unixZeit)` liefert die `Collecting.Options` `{ capacityMultiplier, coinMultiplier }`. Tank-Faktor: `bigTankMultiplier` mit Pass, sonst 1. Münz-Faktor: (`doubleCoinsMultiplier` mit Pass, sonst 1) × (`coinBoost.multiplier`, solange `unixZeit < boosts.coinsUntil`, sonst 1), also multiplikativ (beides zusammen 4-fach, so entschieden; die Bewertung steht in `docs/balance/passes_4_4.md`). Faktoren aus den Daten unter 1 oder kaputt zählen als 1. `Collecting.capacityOf` prüft `capacityMultiplier` selbst (kein number, NaN, unendlich, ab 0 abwärts: 1; Security-Review 4.4). `Collecting.pricePerSand`, `priceOf`, `tankValue` (auch für Sand ohne Mix-Eintrag) und `sell` nehmen optional `options` und multiplizieren den Münz-Faktor als eigenen Faktor; kaputte Werte (kein number, NaN, unendlich, ab 0 abwärts) zählen als 1. Ohne Options rechnet alles genau wie vor 4.4 (Lune-Test vergleicht). `Sandstorm.runTotal`, `preview`, `check` und `apply` reichen `options` an `tankValue` weiter, Vorschau und Sturm rechnen also wie der Verkauf, und `runEarned` enthält die vervielfachten Münzen.
- **Sand-Service:** `Sand.optionsFor(player)` (`Perks.options(profile, os.time())`, ohne Profil `{}`). Alle Collecting-Aufrufe (`settle`, Takt, `setHolding`, `sell`, `setZone`, Snapshot mit `capacityOf`, `pricePerSand`, Sandsturm-Vorschau) bekommen diese Options; `Upgrades.onPrestige` gibt sie an `Sandstorm.apply`. Läuft der Boost ab, sendet der Takt den Zustand neu (Vergleich mit dem zuletzt gesendeten `coinMultiplier`).
- **Münz-Boost:** Zeit läuft in echter Zeit (Unix), auch offline (so entschieden). `Perks.extendCoinBoost(boosts, jetzt, sekunden)` gibt eine neue Tabelle mit `coinsUntil = max(jetzt, gültige Endzeit) + sekunden` zurück (kaputte Endzeit zählt als abgelaufen, andere Felder bleiben, keine Obergrenze, aber endlich; kaputte Uhr oder Dauer: nil, der Kauf bucht dann nicht). `Perks.coinBoostSeconds` = Restsekunden ab 0. Der Handler `Perks.coinBoostHandler(os.time)` wird im `Start` von Passes über `Shop.registerProduct("coin_boost", ...)` eingehängt, rechnet auf der Profil-Kopie von Purchases, wartet nie und gibt `{ changes = { boosts = neueTabelle }, gems = 0, announce }` zurück. Die Schema-Prüfung von Purchases lässt die Tabelle unverändert durch (Lune-Test, auch mit weiteren Feldern). Nach dem bestätigten Speichern: `Notify { kind = "boostBought", productId, addedSeconds, coinBoostSeconds }`. Derselbe Beleg verlängert nur einmal, ProductId 0 kommt über den Echtpfad nie durch.
- **Auto-Dig:** Aktiv mit Pass `autoDig` und `settings.autoDig == true` (`Perks.autoDigActive`). Der Takt des Sand-Service ruft `Perks.collectTick(state, profile, t, options, darfSammeln, merker)`: erst das laufende Sammeln abrechnen wie vor 4.4, dann `Perks.autoDigStep`: Platz im Tank und der Spieler darf sammeln (lebt, nicht am Stand) → Halten starten oder `holdUntil` erneuern; Tank voll (kein ganzes Korn passt, `Collecting.space`) → nicht halten, `tankFull` genau einmal je Füllung und nur, wenn der Spieler sammeln könnte; gerade abgeschaltet (Schalter aus oder Pass weg) → Halten sofort beenden (hält der Spieler die Taste selbst, startet seine nächste Auffrischung es neu). Nach dem Verkauf läuft es von selbst weiter. `SetCollecting(false)` stoppt Auto-Dig nicht (`Perks.wantsCollecting`). War Auto-Dig nie aktiv, tut der Schritt nichts: Verhalten exakt wie vor 4.4.
- **Remote `SetAutoDig(enabled)`:** RemoteEvent, Schema `{ boolean }`, Limit 2 pro s. Der Handler (Passes) schreibt nur `profile.settings` als neue Tabelle (`Perks.withAutoDig`), mit `Sand.settle` davor und `Sand.refresh` danach; ohne Änderung passiert nichts. Ohne Pass wird nur die Einstellung gespeichert.
- **StateSync (fester Vertrag mit der Client-Oberfläche):** `passes` (Kopie `{ [passId] = true }`, nur bekannte Pässe), `autoDig` (Einstellung, Boolean, auch ohne Pass), `autoDigOwned` (Boolean), `coinMultiplier` (Zahl, Pass mal Boost jetzt), `coinBoostSeconds` (Restsekunden ab 0, Server-Uhr beim Snapshot). `capacity` und `pricePerSand` enthalten die Faktoren schon.
- **DataCheck (`checkPerks`):** Jeder Gamepass hat ein bekanntes `perk`, jedes `perk` gehört genau einem Gamepass, andere Produkte haben keins; `doubleCoinsMultiplier`, `bigTankMultiplier` und `coinBoost.multiplier` endlich und größer als 1; `coin_boost` ist Developer Product und Verbrauchsprodukt. Dass `coin_boost` einen Handler hat, prüft `Shop.AfterStart` (`missingHandlers`, Lune-Test in `tests/passes.spec.luau`).
- **Studio-Hilfe:** Nur in Studio (Befehlszeile Ansicht "Server"): `game.Players.<Name>:SetAttribute("DebugPass", "big_tank")` schaltet einen Pass an, `"-big_tank"` aus (gleicher Schreibweg mit settle und refresh, gespeichert im Studio-DataStore); das Attribut wird danach zurückgesetzt, unbekannte IDs erscheinen im Output. `DebugPurchase` im Shop nimmt jetzt auch registrierte Produkte über ihre Daten-ID (`"coin_boost"`, `"coin_boost:fest1"`), über `Purchases.processDebug` mit demselben Ablauf und PurchaseId mit Präfix `studio:`; Gamepasses stehen nicht in der Produktliste von Purchases und gehen nie über diesen Weg. Außerhalb von Studio gibt es keinen Listener und `allowDebug` ist false.
- **Bekannte Grenzen:** Das echte Verhalten von `UserOwnsGamePassAsync` (Zwischenspeicher, Fehlerraten), `PromptGamePassPurchaseFinished` und Studio-Testkäufen ist nur in Studio und im Live-Test prüfbar. Kennt Roblox einen Live-Kauf auch nach den drei Bestätigungsrunden (gut 20 s) noch nicht, wirkt der Pass erst beim nächsten Beitreten. Verliert ein Spieler einen Pass (Rückerstattung), merkt der Server das erst beim nächsten Laden, nach zwei "nein" im Abstand von 60 s. Der Münz-Faktor wirkt nicht auf verkaufte Duplikate von Funden (fester Wert beim Fund, wie in 2.6); das Balance-Dokument nimmt "aus allen Verkäufen" an. Auto-Dig sammelt überall außer am Stand, auch auf dem Rückweg (die Wegfrage aus 1.2 und 6.1 gilt hier verstärkt). Beim Abschalten verliert ein Spieler, der zugleich die Taste hält, höchstens `holdRefreshSeconds` Sammelzeit.

## Shop und Angebote (Paket 4.5)

- **Grundsatz:** Angebote sind Developer Products mit festem Inhalt, gekauft über ProcessReceipt wie Gem-Pakete und Münz-Boost. Der Client sendet zu Angeboten nichts (keine neue Remote), Zustand und Zeit bestimmt der Server mit seiner Unix-Uhr (`os.time`). Regeln im reinen Modul `Logic/Offers` (Lune-Tests `tests/offers.spec.luau`), Daten in `Data/Offers`, der Service `Offers` (in `SERVICE_NAMES` nach Finds, zwischen Passes und Shop) schließt Finds, PlayerData, Sand, Shop und Notify an.
- **Daten (`Data/Offers`, eine Zeile je Angebot):** `{ id, productId, trigger, minRarityId, windowHours, gems, items, priority }`. Starterpaket: `id = "starter"`, `productId = "starter_pack"` (149 Robux, `oneTime`), `trigger = "firstFindFromRarity"`, `minRarityId = "rare"`, `windowHours = 24`, `gems = 300`, `items = { "toolVariant_rare_1" (Glasschaufel), "companion_uncommon_1" (Wüstengecko) }`, `priority = 1`. Entscheidung: Das Angebot erscheint direkt nach dem ersten Fund ab "Selten" und ist ab dann 24 Stunden kaufbar (die Zeit läuft auch offline). Feste Items, kein Zufall (sonst bezahltes Zufallsitem; deshalb gilt `ArePaidRandomItemsRestricted` hier nicht und es gibt keine Quoten). Die Angebots-ID ist Schlüssel im Profil und wird nie umbenannt, ein Angebot wird nie gelöscht.
- **Spielstand (Version 7):** `profile.offers = { [offerId] = { since, bought } }` (`since` Unix-Zeit des Fensterstarts, 0 = nicht gestartet). `Migrations.steps[6]` legt nur eine fehlende Tabelle an, die Einträge je Angebot füllt `Profile.migrate` aus dem Standardprofil (ein neues Angebot braucht so keine Migration). `Profile.sanitize` (über `Offers.cleanOffers`): je Eintrag genau `{ since, bought }`, `since` endlich ab 0 (sonst 0), `bought` Boolean (sonst false), Nicht-Tabellen bei bekannten Angeboten zurückgesetzt, bei unbekannten entfernt, Nicht-Text-Schlüssel und weitere Felder entfernt. Abweichung vom Plan (bewusst): Unbekannte Angebots-IDs mit gültigem Eintrag bleiben gespeichert und wirken nicht, damit ein Merker "gekauft" eines neueren Servers (neues Angebot ohne neue Profil-Version) beim Spielen auf einem älteren Server nicht verloren geht und ein Einmalkauf nie ein zweites Mal angeboten wird. Eine Startzeit in der Zukunft bleibt stehen, `stateOf` entscheidet. Der Sandsturm behält `offers` (`Sandstorm.KEEP_FIELDS`), Funde bleiben ohnehin.
- **Zustand (`Offers.stateOf(profil, offerId, jetzt)` → Zustand, Restsekunden):** `"bought"` (gekauft, gilt immer), `"hidden"` (nicht gestartet; kaputte Startzeit: kein number, NaN, unendlich, ab 0 abwärts oder mehr als `FUTURE_TOLERANCE_SECONDS` = 300 s nach der Server-Uhr; ebenso unbekannte Angebote und eine kaputte Uhr), `"active"` von `since` bis ausschließlich `since + windowHours × 3600` (Restsekunden aufgerundet, also ab 1; ein Start knapp in der Zukunft gilt als gerade gestartet, Restzeit höchstens das ganze Fenster), danach `"expired"`. `Offers.snapshot` liefert alle Angebote aus den Daten.
- **Auslöser (`Offers.onFind`):** Der Finds-Service meldet jeden gebuchten Fund über `Finds.addFindListener(fn(player, profil, { findId, rarityId, isNew, studio }))` nach der Fund-Meldung und vor `Sand.refresh`, auch die Studio-Funde aus `DebugFindSet`/`DebugFindZone` (je neu eingetragenem Fundstück). Der Offers-Service ruft `onFind` mit der Server-Uhr: Jedes Angebot mit `firstFindFromRarity`, das nicht gekauft und nicht gültig gestartet ist, startet bei Seltenheit ab `minRarityId` (Rang aus `Data/Rarities`). Die neue Tabelle wird ohne Warten zugewiesen, danach `Notify { kind = "offerUnlocked", offerId, secondsLeft }`; der folgende `Sand.refresh` von Finds schickt den Zustand. Spätere Funde verschieben nichts. Kisten-Items laufen nie durch Finds und starten nichts (Lune-Test mit einer Goldkiste).
- **Alte Spielstände (`Offers.migrateStart`):** Beim Laden (`PlayerData.onLoaded`) startet das Fenster jetzt, wenn `profile.finds` schon einen bekannten Fund ab `minRarityId` enthält und noch kein Start gesetzt ist; bei einer Änderung `Sand.refresh`, keine Meldung. Läuft bei jedem Laden, ändert aber höchstens einmal und nie ein gekauftes Angebot. Die reine Migration kennt keine Uhr, darum hier.
- **Kauf (`Offers.offerHandler(offerId, uhr, log)`):** Der Service registriert im `Start` je Angebot `Shop.registerProduct(angebot.productId, ...)`. Der Handler rechnet auf der Profil-Kopie von Purchases, ändert sie nicht und wartet nie: `changes = { gems (über Gems.grant, gekappt bei maxGems), inventory (neue Tabellen, je Item +1 im Feld aus Equipment.INVENTORY_FIELDS), offers (bereinigt, bought = true, since bleibt) }`, `gems` = tatsächlich gutgeschriebene Gems (Kaufprotokoll). Bezahlt ist bezahlt: Ein Beleg außerhalb des Fensters (verborgen, abgelaufen) oder nach einem früheren Kauf wird gutgeschrieben (sonst NotProcessedYet für immer), das Protokoll nennt es (`[Offers] ... trotzdem gutgeschrieben`), ebenso ein Kappen bei maxGems. nil nur bei kaputten Daten (unbekanntes Angebot oder Item, falsches Produkt, ungültige Gems). Nichts wird ausgerüstet. Nach dem bestätigten Speichern: `Notify { kind = "offerBought", offerId, gems, items }`, danach sendet der Shop den Zustand (Angebot auf "bought"). Doppelter Beleg, Speicherfehler, Absturz und nicht geladenes Profil laufen über den unveränderten Ablauf aus 4.1 (Lune-Tests mit "starter_pack").
- **StateSync (fester Vertrag mit der Client-Oberfläche):** `offers = { [offerId] = { state = "hidden" | "active" | "expired" | "bought", secondsLeft } }` für jedes Angebot aus `Data/Offers`, Server-Uhr beim Snapshot. Läuft ein Angebot ab, zeigt erst der nächste Snapshot "expired"; der Client zählt `secondsLeft` selbst herunter. Inhalt und Preis liest der Client aus `Data/Offers` und `Data/Products` (dieselben Tabellen wie der Server).
- **Hinweise beim Client (`Offers.nextHint(offersState, ctx, data?)` → offerId oder nil, rein, in shared):** `ctx = { revealBusy, tutorialActive, windowOpen, shownThisSession = { [offerId] = true }, hintVisible? }`. Nur Angebote mit `state == "active"` und `secondsLeft > 0`; nichts, solange ein Reveal läuft oder wartet, das Tutorial läuft, ein Fenster offen oder schon ein Hinweis sichtbar ist (die drei Pflichtfelder müssen genau false sein); je Angebot höchstens einmal pro Sitzung (der Client trägt das gezeigte Angebot sofort in `shownThisSession` ein); mehrere nach `priority` (kleiner zuerst), bei Gleichstand nach ID. Die Meldung `offerUnlocked` kommt nach der Fund-Meldung, der Client kann den Hinweis also hinter den Reveal stellen.
- **DataCheck (`checkOffers`):** eindeutige IDs; `productId` steht in `Products`, ist Developer Product mit `oneTime = true` und gehört zu genau einem Angebot; bekannter Auslöser (`Offers.TRIGGERS`) und bekannte `minRarityId`; `windowHours` endlich und größer als 0; `gems` ganze Zahl von 0 bis `maxGems`; `items` lückenlose Liste fester IDs aus `CrateItems` (eine Kisten-ID wird als "Kiste (Zufall)" gemeldet), je Art höchstens eines; nicht leer (Gems oder Items); `priority` endlich; keine weiteren Felder (zum Beispiel `crateId`). Tests in `tests/data.spec.luau` ("Angebote (4.5)").

## Policy-Funktionen (Paket 4.6)

- **Grundsatz:** Regeln aus [Roblox: Paid random items](https://create.roblox.com/docs/en-us/production/monetization/paid-random-items) (gelesen am 20.11.2026): alle möglichen Ergebnisse mit echten Prozenten vor dem Kauf, Summe 100 % (Rundung mit Hinweis), Quoten-Veränderer (unsere Pity) mit Zahlen erklärt und je Spieler aktuell; bei `ArePaidRandomItemsRestricted` kein Zufallsgenerator mit Robux oder Robux-Währung, Ersatz zum Beispiel fester Kauf zum Erwartungswert. Checkliste und Fragebogen-Vorlage: `docs/fragebogen.md`, Plan: Claude-Dokument "Paket 4.6: Policy-Funktionen, Plan".
- **Quoten der nächsten Öffnung (`Logic/CrateRoll`):** `effectiveOdds(crate, counters)` → `{ odds, total, guarantee }` (ohne anstehende Garantie die Tabelle aus `Data/Crates`, sonst nur die Seltenheiten ab der garantierten Stufe, Quote = Gewicht / total). `roll` würfelt die Seltenheit über genau diese Funktion; ein Lune-Test vergleicht über 216.240 feste Würfe mit der alten Rechnung (gleich). `itemOdds(crateId, counters)` → je Item `numerator / denominator` als exakter Bruch (Summe genau 1), sortiert nach Seltenheit absteigend; unbekannte Kiste: leere Liste. `longRunRates(crate)` → Langzeit-Rate je Seltenheit mit Pity, exakt über einen Zyklus der Markov-Kette (Gold: Legendär 0,0484810690, Mythisch 0,0053867854, wie `docs/balance/crates_4_2.md`).
- **Anzeige (`Logic/OddsView`, rein; `Controllers/CrateShop`):** Die Kisten-Karte zeigt immer die normale Tabelle "Quoten je Öffnung" (jedes mögliche Ergebnis, auch im 10 + 1 Paket, wo nach einer Garantie wieder normal gewürfelt wird; Sicherheitsprüfung 4.6, H1). Steht eine Garantie an, nennt ein Satz zusätzlich ihre Quoten ("Deine nächste Öffnung ist garantiert Episch oder besser: Episch 75 %, Legendär 22,5 %, Mythisch 2,5 %"). Dazu die Zähler bis zur Garantie mit Kosten in Gems und, wenn eine Garantie ins 10 + 1 Paket fällt, die Öffnung, bei der sie spätestens greift. Der Knopf "Details: alle Items und Quoten" öffnet ein eigenes Fenster: die normale Tabelle je Seltenheit mit "Quote je Item" und jedem Item, danach je Pity-Stufe die Tabelle einer garantierten Öffnung (ebenfalls je Item), die Pity-Regel in Zahlen, der Satz zum Paket und der Rundungshinweis (`OddsView.ROUNDING_NOTE`). Prozente ab 0,1 % mit zwei Nachkommastellen, darunter drei gültige Stellen (nie "0 %" für ein mögliches Ergebnis). Das Fenster rechnet bei jedem neuen Pity-Stand neu.
- **Policy-Zustand:** `PolicyCache.state(userId)` → `none`, `pending`, `allowed`, `restricted`, `unknown` (alle Versuche gescheitert). `Crates.policyState(player)` (in Studio vom Attribut `DebugCratesRestricted` überschrieben) geht als `cratePolicy` in den StateSync, neben `cratesAllowed`. Fail-closed bleibt: Kisten nur bei `allowed`.
- **Direktkauf (`Logic/DirectShop`, rein; Handler im Service `Crates`):** offen nur bei `restricted` oder `unknown` (`DirectShop.isOpen`), nie bei `pending` oder `allowed`. Preis je Item aus den Daten, keine eigene Preistabelle (`Economy.directShop = { roundSignificantDigits = 2, monotoneFloor = true, crates = { "iron", "gold" } }`): je Gem-Kiste der Liste, die das Item enthält, Einzelpreis / (Rate der Seltenheit je Öffnung / Poolgröße), bei Kisten ohne Pity in ganzen Zahlen, bei Gold mit `longRunRates`; das Minimum, aufgerundet auf zwei gültige Stellen; danach Untergrenze: eine Seltenheit kostet mindestens so viel wie das günstigste Item jeder niedrigeren. Kein Preis für Event-Items. Ergebnis heute: Gewöhnlich 1.200, Ungewöhnlich 1.200 (Untergrenze, EV 1.000), Selten 2.000, Sandadler 5.100, Episch 8.000, Legendär 25.000, Mythisch 230.000 Gems (`docs/balance/directshop_4_6.md`). `DirectShop.catalog()` ist die Liste für den Client (gleiche Funktion, gleiche Preise). `DirectShop.buy(profil, itemId, { policyState })`: Gründe in dieser Reihenfolge `unknownItem`, `notOffered`, `cratesAllowed`, `noProfile`, `notEnoughGems`; dann ein Block ohne Warten wie `CrateOpen` (Arbeitskopien in einer Koroutine, Fehler oder Warten: `error`, nichts gebucht): `Gems.spend` genau den Preis, Inventar +1. Kein Zufall, keine Pity-Änderung, nichts wird ausgerüstet. Antwort `{ ok, itemId, price, gems, copies }`, danach `Sand.refresh`. `OpenCrate` und `BuyDirectItem` teilen sich die Sperre `busy` je Spieler.
- **Remote `BuyDirectItem(itemId)`:** RemoteFunction, Schema `idIn(CrateItems.byId)`, 2 pro s. Ein Aufruf kauft genau ein Item (bewusst nicht idempotent je Anfrage; Doppeltippen fangen Limit und Client-Sperre).
- **Oberfläche:** Im Shop (`Controllers/GemShop`) ersetzt der Reiter "Direktkauf" den Reiter "Kisten", solange `cratePolicy` gesperrt oder unbekannt meldet und Kisten nicht erlaubt sind: Einleitung, je Item Name, Seltenheit, Art, Bonus, Besitz und Preis, Knopf kauft über die Remote. Das Ausrüstungs-Fenster nennt bei leerem Slot den Direktkauf statt der Kisten.
- **Echte Robux-Preise (N7, H1):** `Controllers/ProductPrices` holt beim Start für jedes Produkt mit ID über 0 einmal Preis und "zum Verkauf" (`GetProductInfoAsync`, sonst `GetProductInfo`, drei Versuche). `Logic/PriceView`: Preis von Roblox, sonst Tabelle; "Bald" bei ID 0, "Nicht verfügbar" bei nicht zum Verkauf; Bonus der Gem-Pakete aus den echten Preisen (für die Tabelle ergibt das die Konzeptspalte, Lune-Test). Der Server prüft beim Start dieselben Produkte (`Purchases.checkDashboard`) und warnt `[Shop] <id>: Preis im Dashboard X Robux, in den Daten Y Robux` bzw. `nicht zum Verkauf`. ProcessReceipt vergleicht `CurrencySpent` mit dem Datenpreis: bei Abweichung Warnung und Feld `currencySpent` im Kaufprotokoll, gebucht wird trotzdem.
- **Ersatzgegenstand Tag 7:** `Economy.daily.day7FallbackItemId = "toolVariant_uncommon_1"` (Kupferschaufel, Bewertung im Balance-Dokument); DataCheck verlangt ein bekanntes Item, das kein reines Event-Item ist. Ausgabe seit 5.1 über `ClaimDaily`: ein Exemplar ins Inventar-Feld seiner Art, bei Policy `restricted`, `unknown` und jedem anderen Zustand außer `allowed` und `pending` (siehe "Daily Reward (Paket 5.1)").
- **Schutztests (`tests/policyguards.spec.luau`):** Glück-Ast, Glücks-Boost (seit 5.1 echt aktiv im Test, auch für die Gratis-Eisenkiste der Daily Reward), Pässe, Münz-Boost und Ausrüstung im Profil ändern weder Quoten noch Würfe einer Kiste. Nur `OpenCrate`, `EquipItem`, `MergeItem`, `BuyDirectItem` und seit 5.1 `ClaimDaily` (Tag 7: Kiste oder Ersatzgegenstand, Schreibstelle `Logic/Daily`) dürfen laut Liste das Inventar ändern, und keine Remote nimmt einen anderen Spieler als Argument. Der Inventar-Test ist eine Textsuche und erkennt allgemeine Schreibwege (zum Beispiel `profile[key] = value` in Purchases für das Starterpaket) nicht.
- **Sicherheitsprüfung 4.6:** kein kritischer Befund. Behoben: Beim 10 + 1 Paket mit anstehender Garantie fehlten Items in der Anzeige (H1, jetzt immer normale Tabelle plus Garantie-Quoten, Lune-Test "die normale Tabelle enthält jedes Item"); Pity-Stand nach einer Öffnung sofort aus der Antwort (M1); Konzept-Checkliste abgehakt, Holzkiste im Fragebogen (M2); Garantie-Quoten in Zahlen; Direktkauf mit zweitem Tipp zur Bestätigung und eigenem Text bei unbekannter Policy. Bewusst offen: "unknown" gilt für die ganze Sitzung (kein erneuter Abruf, fail-closed, Rejoin fragt neu); kommt `PlayerRemoving` eines alten Spielers nach `PlayerAdded` des neuen, bleibt der Zustand "none" bis zum Rejoin (fail-closed); Gem-Ausgaben im Direktkauf werden nicht protokolliert; `spent.robux` zählt den Datenpreis, und mit Regionalpreisen von Roblox warnt `CurrencySpent` bei jedem abweichenden Beleg (nur Protokoll); die Event-Kiste braucht mit der Saison (5.x) dieselbe Karte, dieselben Details und einen Test.
- **Bekannte Grenzen:** Preisprüfung auf dem Server nur beim Start. Studio-Testkäufe lösen vermutlich `CurrencySpent`-Warnungen aus. Echtes Verhalten von `GetProductInfoAsync`, `PolicyService` und der Fenster am Handy ist nur in Studio prüfbar. Bei `unknown` (alle Abfragen gescheitert) öffnet der Direktkauf auch für Spieler aus erlaubten Regionen; die Preise liegen nie unter dem Erwartungswert, Vorteil gibt es also keinen.

## Quoten-Simulation (Paket 4.7)

- **Skript:** `lune run scripts/cratesim [Öffnungen je Kiste und Lauf] [Startwert] [Berichtsdatei]` (Standard 1.000.000, Startwert 470, Bericht `docs/balance/crates_sim_4_7.md`; der Standardaufruf überschreibt den Referenzbericht, für Probeläufe eine eigene Berichtsdatei angeben). Kern in `scripts/lib/cratesim.luau`, eigener Zufallsgeber mit Startwert: gleicher Startwert, gleicher Bericht (nur die Zeilen "Laufzeit" ändern sich). Endet mit Code 1, wenn eine Schwelle verletzt ist.
- **Ablauf:** Jede Kiste (Holz, Eisen, Gold, Event; Event für den Lauf in der Saison) wird über den echten Kaufweg `CrateOpen.open` geöffnet, einmal nur einzeln und einmal nur als 10 + 1 Pakete; die Pity läuft im Profil weiter. Gezählt werden Seltenheiten, Items, Pity-Strecken (auch über Paketgrenzen) und gegriffene Garantien; Bezahlung, Inventar und Pity-Zähler werden je Öffnung gegengeprüft.
- **Sollwerte und Schwellen:** Holz und Eisen gegen die Tabelle, Gold und Event gegen `CrateRoll.longRunRates`, Items gegen Rate der Seltenheit / Poolgröße. Jeder Wert höchstens 4 Standardabweichungen; Seltenheiten ab 10 % zusätzlich unter 1 % relativer Abweichung (bei 1 Mio., skaliert mit √(1 Mio./n)); Chi-Quadrat über alle Items p > 0,001; Seltenheiten mit 0 % nie; Pity nie mehr als 14 Öffnungen ohne Episch oder besser und 59 ohne Legendär oder besser. Pity-Kisten: Mittelwerte über 100 Blöcke (die Öffnungen hängen voneinander ab), Items innerhalb ihrer Seltenheit exakt, Seltenheiten mit Hotelling-T² (5 σ). Methode und Begründung im Bericht.
- **Ergebnis (Referenz 10 Mio. je Kiste und Lauf, Startwert 470, etwa 5 min):** alle Schwellen eingehalten, größte Abweichung 3,29 σ (Holz, ein episches Item), Pity-Strecken genau 14 und 59, keine Abweichung zwischen Kaufweg und Würfen. Der 1-Mio.-Lauf dauert etwa 30 s.
- **Lune-Test:** `tests/cratesim.spec.luau` mit etwa 20.000 Öffnungen je Kiste über denselben Kern, unter 1 s.
- **Wann neu laufen lassen:** nach jeder Änderung an `Data/Crates`, `Data/CrateItems`, `Logic/CrateRoll` oder `Logic/CrateOpen` und einmal vor dem Start (Prüfstelle B).

## Daily Reward (Paket 5.1)

- **Grundsatz:** Der Client schickt nur `ClaimDaily()` ohne Argumente. Tag, Serie, Belohnung und Zeit bestimmt der Server mit seiner Unix-Uhr (`os.time`), nie mit einer Zeit vom Client. Regeln im reinen Modul `Logic/Daily` (Lune-Tests `tests/daily.spec.luau`), Werte in `Economy.daily` und `Economy.luckBoost`. Der Service `Daily` (am Ende von `SERVICE_NAMES`) schließt Remote, Uhr, Policy (`Crates.policyState`), Zufall, PlayerData und StateSync an. `Events` bleibt für Kalender, Saison und Koloss.
- **Regeln:** Ein Tag ist ein UTC-Kalendertag, `Daily.dayOf(t) = floor(t / 86400)` (86399 ist Tag 0, 86400 Tag 1). Gespeichert wird `profile.daily = { streak, lastDay }` (streak = abgeholte Tage der laufenden Serie, lastDay = Tag der letzten Abholung, 0 = nie). Abholbar, wenn gestartet und `lastDay < heute`. Bei `lastDay = heute - 1` kommt der nächste Serientag (streak + 1, nach Tag 7 wieder Tag 1), bei `lastDay < heute - 1` Tag 1. Zweimal am selben Tag: `alreadyClaimed`. Ein `lastDay` ab heute (Zukunft, zum Beispiel von einem Server mit vorgehender Uhr) zählt wie "heute abgeholt", es gibt also nie zwei Belohnungen am selben Tag. Länge der Serie = `#days + 1`. Kaputte Werte im Profil: streak ganz von 0 bis zur Länge (sonst 0 bzw. gekappt), lastDay ganz ab 0 (sonst 0).
- **Start:** Knoten `Economy.daily.startNodeId` gekauft (`collect_tool_2`, die Schaufel, aus den Daten; DataCheck: steht in UpgradeTree und wird nicht vergeben) oder `prestiges >= 1`. Der Sandsturm setzt die Knoten zurück, die Serie läuft weiter (`daily` und `boosts` stehen in `Sandstorm.KEEP_FIELDS`). Vorher `notStarted`.
- **Belohnungen (`Economy.daily`, Werte aus `docs/balance/phase0_startwerte.md`):** Tag 1 `{ kind = "coinBoost", seconds = 600 }`, Tag 2 `{ kind = "gems", amount = 5 }`, Tag 3 `coinBoost` 900 s, Tag 4 `gems` 10, Tag 5 `{ kind = "luck", seconds = 900 }`, Tag 6 `gems` 20, Tag 7 `{ kind = "crate", crateId = "iron" }`, dazu `day7FallbackItemId`. Münz-Boost über `Perks.extendCoinBoost` (Faktor `Economy.coinBoost.multiplier` = 2, verlängert ab der alten Endzeit oder ab jetzt), Glücks-Boost über `Perks.extendLuckBoost`, Gems über `Gems.grant` mit Quelle `daily:day<N>` (gekappt bei `maxGems`; die Abholung gilt trotzdem, die Antwort nennt die gutgeschriebene Menge und `capped = true`). Die alten Datenfelder `boost`, `boostId`, `durationSeconds` gibt es nicht mehr. DataCheck (`checkDaily`): genau 6 Tage in Reihenfolge, je Art nur ihre Felder (ein Tippfehler wie `durationSeconds` fällt auf), Sekunden und Gems ganze Zahlen über 0, Gems höchstens `maxGems`, Tag 7 die Eisenkiste (bekannt, keine Event-Kiste), Startknoten, `luckBoost.multiplier` endlich und größer als 1.
- **Tag 7 und Policy:** Bei `allowed` die Eisenkiste gratis über `CrateOpen.openFree` auf einer flachen Arbeitskopie des Profils (eine Öffnung, derselbe Wurf wie bei OpenCrate, zählt für die Pity; Eisen hat keine). Bei `restricted`, `unknown` und jedem anderen Zustand außer `pending` (auch `none`, fail-closed): ein Exemplar des Ersatzgegenstands im Inventar-Feld seiner Art, kein Zufall. Bei `pending` (erste Abfrage läuft): `policyPending`, nichts gebucht. Der Service wartet dann ohne Sperre bis `POLICY_WAIT_SECONDS` = 6 s (Abfrage alle 0,25 s) und versucht es einmal neu; läuft die Abfrage dann noch, bleibt es bei `policyPending`.
- **Kein halbes Buchen:** Wie CrateOpen und DirectShop. Zuerst die Gründe in dieser Reihenfolge: `noProfile`, `error` (kaputte Uhr), `notStarted`, `alreadyClaimed`, `policyPending` (nur Tag 7). Dann rechnet eine eigene Koroutine auf Arbeitskopien (Gems, Boosts, Pity, Inventar, neue Serie). Wirft oder wartet sie, wird nichts geschrieben: `error`, der Text (`detail`) geht nur ins Protokoll (`[Crates] Daily Reward für ...`). Danach weist derselbe Thread nur fertige Werte zu (`daily` und je nach Belohnung `gems`, `boosts`, `pity`, `inventory`). Belohnung und Serie gibt es zusammen oder gar nicht.
- **Glücks-Boost:** `profile.boosts.luckUntil` (Unix-Zeit). Neu in `Profile.default`, alte Spielstände bekommen 0 über `Profile.migrate` (keine neue Profilversion), `sanitize` setzt negative Werte auf 0 (NaN, unendlich und falscher Typ wie bei `coinsUntil`). `Perks.luckBoostActive`, `luckBoostSeconds`, `luckBoostMultiplier` (Faktor `Economy.luckBoost.multiplier` = 2, solange `jetzt < luckUntil`, sonst 1; kaputt oder unter 1 zählt als 1) und `extendLuckBoost`. `FindRoll.chancePerSecond(profil, zone, serverTime, data?, unixTime?)` multipliziert ihn als eigenen Faktor neben Zone, Glück-Ast und Wetter (Ergebnis höchstens 1). Die Uhr ist `unixTime` (der Finds-Service gibt `os.time()` als `Input.unixTime` mit), fehlt sie, zählt `serverTime`. Er ändert nur, ob ein Fund fällt, nie Seltenheit, Fundstück oder Wert und nie Kisten (CrateRoll und CrateOpen lesen keine Boosts; Tests in `tests/findroll.spec.luau`, `tests/policyguards.spec.luau`, `tests/daily.spec.luau`).
- **Remote `ClaimDaily`:** RemoteFunction, Schema `{}`, Limit 1 je 2 s. Läuft unter `Crates.runExclusive`, derselben Sperre je Spieler wie OpenCrate und BuyDirectItem (ein gleichzeitiger Aufruf bekommt `busy`), dazu eine eigene Sperre während des Wartens auf die Policy. Ohne aktive Sitzung (`PlayerData.isActive`) gibt es `noProfile`. Antwort `{ ok = true, day, reward, crate? }` mit `reward` = `{ kind = "coinBoost", seconds }`, `{ kind = "luck", seconds }`, `{ kind = "gems", amount, capped? }`, `{ kind = "crate", crateId, itemId }` oder `{ kind = "fixedItem", itemId, copies }`. `crate` gibt es nur bei der Kiste, im Format der OpenCrate-Antwort (`ok, crateId, count, results, highest, pity, gems, coins, free`), damit der Client denselben Reveal zeigt. Fehler: `{ ok = false, reason }` mit `notStarted`, `alreadyClaimed`, `policyPending`, `noProfile`, `busy`, `error`. Nach Erfolg sendet `Sand.refresh` den Zustand. Gespeichert wird wie bei den Kisten über das Autosave von ProfileStore. Ein Aufruf über dem Limit wird von `Net` verworfen, die RemoteFunction gibt dann `nil` zurück.
- **StateSync (fester Vertrag mit der Client-Oberfläche):** `daily = { started, day, canClaim, secondsLeft, streak }` aus `Daily.state` (Server-Uhr beim Snapshot): `day` ist der Serientag der nächsten Abholung (jetzt, wenn `canClaim`, sonst nach `secondsLeft`), `secondsLeft` ist 0, wenn abholbar oder nicht gestartet, sonst die Sekunden bis 0 Uhr UTC des nächsten abholbaren Tages (aufgerundet), `streak` sind die abgeholten Tage, die noch zählen (0 nach einem verpassten Tag; nach Tag 7 bis zum nächsten Abholen 7). Dazu `luckBoostSeconds` (Restsekunden des Glücks-Boosts, ab 0, wie `coinBoostSeconds`). Ein Takt alle `DAY_CHECK_SECONDS` = 5 s sendet beim Tageswechsel allen geladenen Spielern den Zustand neu; Restzeiten zählt der Client selbst herunter.
- **Studio-Hilfe:** Nur in Studio (Befehlszeile Ansicht "Server"): `game.Players.<Name>:SetAttribute("DebugDaily", "reset")` (Serie leer, Tag 1 abholbar), `"yesterday"` (als wäre gestern abgeholt, die Serie bleibt, der nächste Tag ist sofort abholbar), `"day:6"` (Serie 6, gestern abgeholt, Tag 7 ist sofort abholbar; erlaubt 0 bis 7). Das Attribut wird danach gelöscht, damit derselbe Befehl erneut wirkt; ein Tippfehler erscheint im Output. Außerhalb von Studio gibt es keinen Listener. `Daily.parseDebug` und `Daily.withDebug` sind rein und getestet.
- **Bekannte Grenzen:** Ein Absturz vor dem nächsten Autosave verliert Belohnung und Abholung gemeinsam (dann ist die Abholung erneut möglich, nie doppelt). Ein `lastDay` weit in der Zukunft (kaputte Daten oder eine falsche Server-Uhr) sperrt bis zum Tag danach. Gehen Server-Uhren auseinander, gibt ein Server mit vorgehender Uhr den neuen Tag einige Sekunden früher; eine Abholung je Tag bleibt sicher. Die eigene Yield-Prüfung von `Logic/Daily` ist heute nur über Codeänderungen erreichbar (der einzige fremde Rückruf, der Zufall, läuft in der Koroutine von CrateOpen; dieser Weg ist getestet). Sperre, Warten auf die Policy, Tageswechsel-Takt und Studio-Hilfe des Service sind nur in Studio prüfbar. Der Glücks-Boost wirkt nur auf Funde aus dem Sammeln (der Offline-Ertrag kommt mit 5.3).

- **Sicherheitsprüfung 5.1:** Kein kritischer oder hoher Befund. Eingearbeitet: `Profile.sanitize` rundet `daily.streak` und `daily.lastDay` auf ganze Zahlen ab 0, die Gratis-Kiste leitet `restricted` aus dem Policy-Zustand ab, Tag 7 zeigt bei gesperrter oder unbekannter Policy nur den Ersatzgegenstand, der Kommentar zur gemeinsamen Sperre nennt genau OpenCrate, BuyDirectItem und ClaimDaily. ## Codes-System (Paket 5.2)

- **Grundsatz:** Der Client schickt nur den eingegebenen Text (`RedeemCode(text)`). Ob er ein Code ist, was er gibt, ob er gilt und ob der Spieler gesperrt ist, entscheidet der Server. Regeln im reinen Modul `Logic/Codes` (Lune-Tests `tests/codes.spec.luau`), der Service `Codes` (nach Daily in `SERVICE_NAMES`) schließt Remote, Uhren, Profil, gemeinsame Sperre und Studio-Hilfe an.
- **Codes nur auf dem Server:** Die Tabelle liegt in `src/server/Data/Codes.luau` (ServerScriptService, nie repliziert). Zeile: `{ id, code, reward, startsAt?, endsAt? }`. `id` ist der Schlüssel im Profil (Buchstaben, Ziffern, `_`, `-`, höchstens 32 Zeichen; nie umbenennen und nie wiederverwenden), `code` der normalisierte Text, `startsAt` und `endsAt` Unix-Zeiten (Server-Uhr), `endsAt` einschließlich. Belohnungen: `{ kind = "gems", amount }` (1 bis 1000), `{ kind = "coinBoost", seconds }` oder `{ kind = "luck", seconds }` (1 bis 86400). Nie Kisten, Items oder Robux. Die zwei Beispiel-Codes (50 Gems, 20 Minuten Münz-Boost) werden vor dem Start durch echte Codes ersetzt. `Logic/Codes` in `src/shared` kennt keinen Code, die Tabelle wird jeder Funktion übergeben. Ein Lune-Test sucht jeden Code-Text der Server-Tabelle in allen Dateien unter `src/shared` und `src/client` (auch in Platzhaltern) und prüft, dass dort kein Code auf `ServerScriptService` oder `server/Data` zugreift.
- **Normalisieren:** `Codes.normalize(text)`: nil bei Nicht-Text; sonst Leerraum am Rand weg (Leerzeichen, Tab, Zeilenende), Großbuchstaben, danach nur `A-Z`, `0-9` und `-`, Länge 1 bis 24, sonst nil. Leerzeichen in der Mitte, Umlaute und Sonderzeichen sind ungültig. Der Vergleich mit der Tabelle läuft über den normalisierten Text (auch der Code der Zeile wird normalisiert).
- **Einlösen:** `Codes.redeem(profil, tabelle, jetzt, text, ctx?)`. Gründe in dieser Reihenfolge: `noProfile`, `error` (kaputte Uhr), `invalid` (Eingabe ungültig oder Code unbekannt), `error` (kaputte Zeile oder `profile.codes` keine Tabelle), `alreadyRedeemed` (Code-ID im Profil, jeder Wert außer nil und false zählt), `invalid` (noch nicht begonnen: jetzt < startsAt; abgelaufen: jetzt > endsAt; kaputte Zeiten zählen wie abgelaufen). Unbekannt, abgelaufen, noch nicht begonnen und ungültig geben genau dieselbe Antwort, damit niemand erfährt, ob es einen Code gibt. Ein schon eingelöster Code nennt `alreadyRedeemed`, auch wenn er inzwischen abgelaufen ist (der Spieler kennt ihn).
- **Belohnungen und kein halbes Buchen:** Wie `Logic/Daily`: Gems über `Gems.grant` mit Quelle `code:<id>` (gekappt bei `maxGems`; die Einlösung gilt trotzdem, die Antwort nennt die gutgeschriebene Menge und `capped = true`), Münz-Boost über `Perks.extendCoinBoost`, Glücks-Boost über `Perks.extendLuckBoost` (ab der alten Endzeit oder ab jetzt). Prüfen und Rechnen laufen in einer eigenen Koroutine auf Arbeitskopien. Wirft oder wartet sie, wird nichts geschrieben (`error`, der Text geht nur ins Protokoll). Danach weist derselbe Thread nur fertige Werte zu: `codes` und `gems` bzw. `boosts`, zusammen oder gar nicht. Beim Einlösen gelten die Obergrenzen (1000 Gems, 86400 s) noch einmal; eine unbekannte Art (Kiste, Item, Robux) ist immer `error`.
- **Falsche Versuche und Sperre:** Konstanten oben im Service: `MAX_FAILURES` = 5, `LOCK_SECONDS` = 60. Die Zähl-Logik ist rein: `Codes.attempt(zustand, jetzt, grenzen, run)` gibt `(Antwort, neuer Zustand)` zurück, Zustand `{ failures, lockedUntil }`. Läuft eine Sperre, wird `run` nicht gerufen und die Antwort ist `locked` mit `secondsLeft` (aufgerundet, ab 1), auch für einen richtigen Code. Nur `invalid` zählt; der fünfte falsche Versuch startet die Sperre und antwortet schon selbst `locked` (secondsLeft = 60). Ein Erfolg setzt den Zähler auf 0, eine abgelaufene Sperre verfällt und der Zähler beginnt neu. `alreadyRedeemed`, `busy`, `noProfile` und `error` zählen nicht. Versuche in der Sperre verlängern sie nicht. Zähler und Sperre liegen nur im Speicher des Servers, je UserId, Uhr `os.clock`. Beim Verlassen wird der Zähler gelöscht; eine laufende Sperre bleibt bis zu ihrem Ende stehen (danach gelöscht), damit ein schneller Rejoin auf denselben Server sie nicht aufhebt.
- **Remote `RedeemCode`:** RemoteFunction, Schema ein Text mit 1 bis 24 Bytes (`Validate.string(maxLen, minLen)`, die Längen kommen aus `Codes.MIN_LENGTH` und `Codes.MAX_LENGTH`), Limit 1 je 3 s. Läuft unter `Crates.runExclusive` (gemeinsame Sperre mit OpenCrate, BuyDirectItem und ClaimDaily, gleichzeitig: `busy`); die Sperre nach falschen Versuchen liegt außen herum. Server-Zeit für Gültigkeit und Boosts: `os.time()`. Ohne aktive Sitzung (`PlayerData.isActive`) gibt es `noProfile`. Antwort: `{ ok = true, reward }` mit `reward` = `{ kind = "gems", amount, capped? }`, `{ kind = "coinBoost", seconds }` oder `{ kind = "luck", seconds }`; `{ ok = false, reason = "locked", secondsLeft }`; sonst `{ ok = false, reason }` mit `invalid`, `alreadyRedeemed`, `busy`, `noProfile`, `error`. Die Antwort nennt nie Code-ID, Code-Text oder `detail`. Nach Erfolg sendet `runExclusive` den Zustand neu (`Sand.refresh`). Gespeichert wird über das Autosave von ProfileStore. Ein Aufruf über dem Limit wird von `Net` verworfen (Antwort `nil`).
- **Prüfung der Tabelle:** `Codes.check(tabelle, data?)` (rein, mit übergebener Tabelle, nicht im Shared-DataCheck, weil die Daten nur auf dem Server liegen). Prüft: lückenlose Liste, nur bekannte Felder je Zeile (ein Tippfehler wie `endAt` fällt auf), eindeutige `id` im erlaubten Format, eindeutiger `code` mit `normalize(code) == code`, bekannte Art mit nur ihren Feldern, Gems ganz von 1 bis 1000 (und höchstens `maxGems`), Sekunden ganz von 1 bis 86400, Zeiten endlich ab 0, `endsAt > startsAt`. Die Fehlertexte nennen die ID, nie den Code. Der Service ruft die Prüfung in `Init` auf; bei Fehlern bricht der Serverstart mit allen Texten ab (wie DataCheck).
- **Profil:** `profile.codes = { [codeId] = true }`. Neu in `Profile.default`, alte Spielstände bekommen `{}` über `Profile.migrate` (keine neue Profilversion). `sanitize` behält nur nicht leere Text-Schlüssel mit Wert true (unbekannte IDs bleiben, damit ein gelöschter Code nicht wieder einlösbar wird), ein falscher Typ des Felds wird `{}`. `codes` steht in `Sandstorm.KEEP_FIELDS`.
- **Studio-Hilfe:** Nur in Studio (Befehlszeile Ansicht "Server"): `game.Players.<Name>:SetAttribute("DebugCodes", "reset")` leert `profile.codes` und hebt Zähler und Sperre des Spielers auf. Das Attribut wird danach gelöscht; ein Tippfehler erscheint im Output. Außerhalb von Studio gibt es keinen Listener. `Codes.parseDebug` ist rein und getestet.
- **Bewusste Grenzen:** Keine globale Obergrenze je Code (jeder Spieler darf jeden Code einmal einlösen, es gibt keine "die ersten 1000"). Die Sperre liegt nur im Speicher je Server: Ein Wechsel auf einen anderen Server beginnt mit leerem Zähler, ein Neustart des Servers löscht alle Sperren. Der Zähler verfällt nicht mit der Zeit, nur durch Erfolg, Sperre oder Verlassen. Ein Absturz vor dem nächsten Autosave verliert Belohnung und Merker gemeinsam (dann ist der Code erneut einlösbar, nie doppelt). Bei vollem Gem-Stand (`maxGems`) gilt der Code als eingelöst, auch wenn 0 Gems gutgeschrieben werden. Die Leerzeichen am Rand zählen im Schema der Remote mit (höchstens 24 Zeichen roh), der Client kürzt die Eingabe am besten vorher. Service-Teile (gemeinsame Sperre, Uhr, Aufräumen beim Verlassen, Studio-Hilfe, Abbruch beim Start) sind nur in Studio prüfbar; die Lune-Tests prüfen davon nur die Konstanten und Aufrufe per Textsuche.

- **Sicherheitsprüfung 5.2:** Kein kritischer oder hoher Befund. Eingearbeitet: Fehlversuche überleben das Verlassen so lange wie eine Sperre (Rejoin setzt den Zähler nicht mehr zurück), der Serverstart außerhalb von Studio bricht ab, solange die Beispiel-Codes `WILLKOMMEN` und `1000LIKES` in `Data/Codes` stehen, der Client prüft das öffentliche Format vor dem Senden und zeigt eine volle Gem-Obergrenze an, der Quelltext-Test sucht ohne Beachtung der Großschreibung. Bewusst offen: die Sperre liegt nur im Speicher je Server (ein Serverwechsel oder Zweitkonten umgehen sie, der Schaden ist je Konto und Code höchstens 1000 Gems oder ein Boost); Code-IDs nie umbenennen oder wiederverwenden (nur als Kommentar, keine Liste gesperrter IDs); `Profile.sanitize` behält nur `true` als Merker.

## Offline-Ertrag (Paket 5.3)

- **Regeln (`Logic/Offline`, rein, Lune-Tests `tests/offline.spec.luau`):** `apply(profil, jetzt)` rechnet beim Laden des Profils die Abwesenheit `jetzt - lastSeen` (Server-Uhr, nie vom Client). Unter `Economy.offline.minSeconds` (300 s) passiert nichts und `lastSeen` bleibt. Grenze `baseHours` (4) oder mit dem Pass "autoDig" `autoDigHours` (12); wer länger weg war, bekommt genau die Grenze (`capped`). Ohne besessenen, ausgestatteten Begleiter (Slot `companion`) gibt es nichts (`noCompanion`). Ertrag = Sammelrate ohne Ausrüstungsbonus mal Sekunden mal `Economy.offline.rateFactor` (0.5) mal Preis des Sands der aktuellen Zone (`Collecting.priceOf`) mal Faktor des 2x-Münzen-Passes. Münz-Boost, Glücks-Boost und Kisten-Items zählen nicht, es gibt nie Funde. Gebucht wird wie `Wind.credit` (`coins` und `runEarned`, nicht in den Tank).
- **Atomar und einmal:** Alles wird zuerst gerechnet (auch die neuen Münzstände), dann werden nur fertige Werte geschrieben (`coins`, `runEarned`, `lastSeen`); wirft die Rechnung, bleibt das Profil unverändert und `lastSeen` stehen (Grund `error`; das nächste Autosave setzt `lastSeen` dann doch neu, der Zeitraum geht verloren). In jedem bezahlten oder leeren Fall außer `tooShort` setzt `apply` `lastSeen` im selben Schritt auf jetzt: derselbe Zeitraum wird nie zweimal bezahlt. Fehlende oder kaputte `lastSeen` geben nichts (`badTime`) und werden auf jetzt gesetzt. `lastSeen` geht nie zurück: `PlayerSession.laterSeen` behält beim Speichern und Verlassen eine Zeit in der Zukunft (Server mit vorgehender Uhr), und `apply` zahlt dann nichts und schreibt nichts (nur über 7 Tage in der Zukunft gilt es als kaputt). Sonst ließe sich eine Uhrdifferenz durch Serverwechsel immer wieder bezahlen.
- **Service `Offline`:** Hängt über `PlayerData.onLoaded` an (läuft nach dem Sand-Service, dessen Zonenprüfung zuerst gilt), zahlt, speichert den Bericht im Speicher des Servers (`id` zählt hoch) und löst ein zweites `Sand.refresh` aus. Keine Remote: Der Client kann nichts auslösen. StateSync-Feld `offline = { id, ok, reason?, seconds, awaySeconds, capSeconds, capped, coins? }` über `Sand.addSnapshotProvider`.
- **Client:** `OfflineCard` zeigt jeden Bericht (`id`) einmal als Karte "Schön, dass du wieder da bist" mit Dauer, Münzen und bei Grenze der Zeile "Grenze erreicht"; ohne Begleiter der Hinweis, einen auszurüsten. Nie während Tutorial, Reveal oder offenem Fenster. Der Pass-Text nennt die 12 Stunden (`Data/Products`).
- **Studio-Hilfe:** `DebugOffline` (Minuten, nur in Studio) setzt `lastSeen` zurück und zahlt sofort.
- **Bewusste Grenzen:** Ein Pass, der beim Laden erst vom Marktplatz bestätigt wird (noch nicht in `profile.passes`), zählt erst beim nächsten Beitritt (zahlt höchstens zu wenig). Nach einem Absturz zählt der letzte Autosave. Der Faktor 0,5 ist ein Vorschlag (Balance, Waltuh kann ihn in `Economy.offline` ändern). Offline-Münzen zählen für den Sandsturm wie verdiente Münzen.
- **Sicherheitsprüfung 5.3:** Kein kritischer oder hoher Befund. Eingearbeitet: `lastSeen` geht nie zurück (M1), ganze Münzen wie beim Verkauf, eine gesperrte aktuelle Zone zahlt den Preis der Startzone, die Karte zeigt die Klammer "mit Auto-Dig" nur ohne Pass, DataCheck prüft `autoDigHours` höchstens 48 und meldet alle Fehler von `Economy.offline`, Kommentare zu `error` und `tooShort` stimmen jetzt. Bewusst offen: ein Pass, der beim Laden noch nicht in `profile.passes` steht oder dort veraltet ist (zu wenig bzw. zu viel bezahlt, wie bei Online-Pässen aus 4.4); der Text von `auto_dig` nennt "12 statt 4 Stunden" fest (Datenänderung braucht eine Textänderung); die Grenze gilt je Abwesenheit, nicht je Tag (Balance: Wer sich alle 4 Stunden kurz einloggt, bekommt rund um die Uhr die Hälfte der Nennrate); `Economy.offline.noFindsFromRarityId` wird nicht mehr gelesen; Offline bucht in einer normalen Zahl, nicht in BigNum (mit den heutigen Tabellen unter 1e17).

## Event-Kalender (Paket 5.4)

- **Bewusste Grenzen:** Event-Zone, Pass, Koloss und Event-Items im Direktshop (Woche 3) folgen in 5.5 bis 5.7 und hängen dann an `phases` und `list`. Zwischen zwei Saisons ist die Event-Kiste gesperrt, Besitz und Pity bleiben im Profil. Gewürfelt wird immer mit der Serverzeit beim Öffnen: Wer genau beim Saisonende öffnet, bekommt je nach Sekunde "notInSeason", nichts wird gebucht. Eine Saison kann nur über eine Datenänderung und einen Serverneustart (neues Release) hinzukommen; laufende Server kennen die neue Zeile erst nach dem Update.
- **Sicherheitsprüfung 5.4:** Kein kritischer, hoher oder mittlerer Befund; `inSeason` kommt nur aus `Events.inSeason` (Server-Uhr), `DebugSeason` ist in Live-Servern doppelt wirkungslos. Eingearbeitet: der Remote-Test prüft jetzt `RemoteSpec.byName`, die gemeinsame "nichts aktiv"-Tabelle ist eingefroren, `lastKey` nur für anwesende Spieler, eigener Text "Diese Woche ist die Event-Kiste geschlossen" für Wochen mit `crateOpen = false`. Für 5.5 offen: Entscheidung, ob Event-Items über den Saison-Pass auch außerhalb der Saison kommen dürfen (dann ggf. DataCheck für Angebote). Serveruhren können leicht abweichen (wie bei Daily und Angeboten).
